## Problem

The study capability exists only inside fusion-tea, and nothing installs it. A new modeling project that uses sysml-codegen and teax cannot run a study without copying fusion-tea files by hand. The capability is the `run-study` skill (`SKILL.md`, `runbook.md`, `record-template.md`), the rulebook `modeling_project/STUDY_POLICY.md`, the tools under `scripts/study/` with seven JSON schemas, and `scripts/integrate.py`.

[OWNER] (epic header, 2026-10-06): the study layer ships from sysml-codegen. sysml-codegen already depends on agentic-mbse, owns the generated-package contracts the tools read, and already has an `install-commands` subcommand.

The bar is a working capability in a fresh target, not copied files. A target that uses sysml-codegen and teax runs `sysml-codegen install-commands` and can then run a study with nothing borrowed from fusion-tea.

Five things make this a port rather than a copy:

- **The tools find the project from their own file location.** `manifest.repo_root()` is `Path(__file__).parents[2]` (fusion-tea `scripts/study/manifest.py:57`). Installed from a wheel, that is a directory inside site-packages, so every repo-relative path and every tool-source digest breaks. Evidence A below has the detail.
- **fusion-tea uses the tools as a library.** About 30 package scripts import `scripts.study.{common, manifest, identity, indicators, verify}`, and six `build.py` files import `scripts.integrate.rederived_census` (`CONSUMER_SURFACE.md`, generated by the orchestrator at fusion-tea `b06585709`).
- **Committed study records name the old tool paths.** The record template stores `tools[].path` as `scripts/study/<tool>.py` (`record-template.md:369`). The orchestrator counted 1,261 to 1,338 committed record files that mention these paths, depending on the pattern. Committed records must not change (epic Out of Scope).
- **`integrate.py` runs fusion-tea's own tests as gates.** Gate 1a runs `tests/test_dependency_provenance.py` and gate 5 runs `tests/models/test_model_family_spines.py`. `rederived_census` imports `_by_entry_type` from that second test module (`integrate.py:1098`).
- **`install-commands` cannot deliver this today.** It copies one Claude command, has no ownership rules, and does not work from a wheel. `get_commands_dir()` resolves `claude/commands/` at the checkout root (`src/sysml_codegen/cli/__init__.py:59`), and the wheel packages only `src/sysml_codegen` (`pyproject.toml`, `[tool.hatch.build.targets.wheel]`).

fusion-tea cannot adopt the moved layer inside this item. Its sysml-codegen pin is `8a758e9` (fusion-tea `pyproject.toml:37`), 142 commits behind this branch's base, and moving the pin also changes the code generator its packages are built with. So this item delivers the sysml-codegen side, and fusion-tea adopts after merge by a runbook (orchestrator decision 1, under Known Requirements § Delivery).

## Success Criteria

- [ ] **SC1. Fresh install from a wheel.** In a scratch target, with sysml-codegen installed from a wheel built from this branch and no source checkout on the path, `sysml-codegen install-commands` installs `run-study` (skill, runbook, record template) for Claude Code and Codex, the study-policy template, and the existing `teax-completion` helper. The listing option names all of them. *Checked by* an install transcript in item evidence and a suite test of the install logic.
- [ ] **SC2. Ownership holds on re-install.** A second `install-commands` run refreshes unmodified skill files, keeps a locally edited skill file (or prompts for it), and leaves an existing `STUDY_POLICY.md` untouched unless the force option is given. Running `agentic-mbse init` afterwards leaves the `run-study` install intact, and the reverse order also holds. *Checked by* suite tests on scratch targets.
- [ ] **SC3. The tools run from the installed package against the neutral fixture.** `indicators`, `preflight` (`gates` and `clean`), `verify` and `integrate` each complete on the fixture when their runtime is present, and each fails closed as documented on at least one negative case. Without teax, a tool that needs teax exits non-zero, names teax in its message and writes no output. *Checked by* the moved and new tests: the default suite, the teax execution lane, and the license-gated tests. Item evidence records one run with both teax and the syside license present, because `integrate` needs both to complete.
- [ ] **SC4. A fresh target runs a study from installed files only.** In a scratch target with no fusion-tea file anywhere, an agent follows only the installed skill, runbook, record template and policy template. It writes the fixture's annex, manifest and axis declaration from that text alone. It then runs one study on the neutral fixture through to a committed record that passes the record checks. A second agent in a fresh session then reads only the record directory and writes the administrator synthesis. *Checked by* a dry-run record in item evidence, in the shape of Item 2's dry run. The evidence names every package-owned piece the fixture supplied ready-made (for example the oracle or the route module).
- [ ] **SC5. The shipped text and tools are generic.** A suite test greps the installed skill, runbook, record template, policy template and every tool module for identifiers, including inside labelled examples. It finds none of: a fusion-tea path (`exploration/`, `.project/`, `scripts/study`, `tests/models`), a fusion-tea package name or key prefix, `era_adapter`, a consumer requirement number (`MR-` followed by a digit), `/home/`, `~/1cfe`, or a `STOP_PARSER_` variable. The test does not check vocabulary: fusion words stay legal in labelled examples. "LCOE" appears only in labelled examples. This extends fusion-tea's `tests/study/test_generic.py` to the instruction files.
- [ ] **SC6. fusion-tea's imports keep working.** Every symbol that fusion-tea's consumer surface imports from `scripts.study.*` and `scripts.integrate` exists in the moved package with the same name, signature and behaviour. *Checked by* a suite test that imports each symbol by name from the list the design enumerates.
- [ ] **SC7. Tool identity is unambiguous and old records stay valid.** Every document the moved tools write names which tool and which revision produced it, and a reader can tell it apart from a pre-move document. No shipped check reads a committed record's tool path or command as a live file. The `indicator-input-fingerprint/v1` recipe and every document `schema_version` string are unchanged. *Checked by* tests and a schema diff against fusion-tea `b06585709`.
- [ ] **SC8. `integrate` judges any target, not fusion-tea.** `integrate` names no target test file, no target environment variable and no target-only dependency. A repo-scope gate the target did not declare appears in the return as not declared, never as a pass. A fixture that declares gates equivalent to fusion-tea's two gets the same ten gates in the same order and the same return shape. *Checked by* tests and the SC5 grep.
- [ ] **SC9. fusion-tea has a rehearsed adoption runbook.** A runbook in the shape of Item 2's covers, in order:
  - a drift check: diff fusion-tea's study skill, policy, tools and `integrate.py` against `b06585709`, and stop on any change until it reaches sysml-codegen or its fusion-tea home;
  - a no-loss check: before anything local is removed, every ledger destination is present in fusion-tea's tree;
  - the pin move;
  - the switch of fusion-tea's copies to thin wrappers or removal;
  - the re-install for both assistants, and removal of the local `run-study`, its `.gitignore` whitelist line and its `.agents/skills` link;
  - the study suite, and the re-verification of one existing record (defined under Known Requirements § Delivery).

  The orchestrator rehearses every step it can on a disposable copy of fusion-tea and records what it observed. Steps that need the merged SHA are marked not rehearsed. This criterion replaces epic Item 3 criterion 3 for this item.
- [ ] **SC10. No loss of information for fusion-tea.** Every fusion-specific line removed from the ported skill, runbook, record template or policy has a row in the shared migration ledger with its fusion-tea destination. Each destination exists on a fusion-tea branch before the sysml-codegen change merges. *Checked by* the ledger rows and that branch's diff.
- [ ] **SC11. Suites pass.** The sysml-codegen full suite (`uv run --env-file <file holding SYSIDE_LICENSE_KEY> pytest tests/`; the orchestrator's baseline used sysml-codegen's main-checkout `.env`) shows the baseline of 2206 passed and 9 skipped, plus the new tests, with no failure other than the known one. The known failure is `tests/conformance/test_self_binding_guidance_contract.py::test_zero_unmarked_self_named_examples_across_all_trees`, and it is not this item's. `ruff` and `mypy` are clean on `src/`. ## Evidence A: the import-repackaging check

The epic names this check as its one untested bet ("Risks" and "De-risking"). The question: can `scripts.study` and `integrate.py` import as a package without the `scripts.` convention, and what happens to `manifest.repo_root()` and to schema lookup?

**How it was done.** I read the code at fusion-tea `b06585709` and classified every root-dependent call. I also wrote an executable check that copies the tools into a scratch package, rewrites the imports, and runs every module, the CLIs and an `indicators` run against `synthetic_pkg`, with a baseline run in fusion-tea's own layout. The script is `.orchestrate-logs/scratch/repack-check/check.py` (gitignored) and runs with `.venv/bin/python .orchestrate-logs/scratch/repack-check/check.py`. The spec session could not run Python (the command needed approval), so the findings below were first written from reading the code.
