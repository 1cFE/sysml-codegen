Q1 — What `in R = <expr>` IS, and RHS name-resolution deferral

VERDICT: `in R = <expr>` is a directed parameter usage (an `in` parameter of the calc usage) carrying a fixed, bound **feature value** relationship. The feature value is a shorthand that induces an implicit nested **binding** between the parameter and the result of the value expression — it is neither a raw connector declaration nor a `default`. RHS name resolution is deferred to KerML scoping; SysML adds no calc-specific rule that hides or specially exposes the calc's own parameters, so ordinary nearest-lexical-scope resolution makes the calc's own `in R` the nearest binding for a bare `R`, shadowing the enclosing part's attribute. This is consistent with the SysIDE observation.

QUOTED NORMATIVE TEXT:
- Feature value definition, Part 1 clause 7.13.4: "A _feature value_ is a relationship between an owning usage and a _value expression,_ whose result provides values for the feature. The feature value relationship is specified as either _bound_ or _initial,_ and as either _fixed_ or _default._" and "A fixed, bound feature value relationship is declared using the symbol `=` ... Usages that have a feature value relationship of this form implicitly have a nested binding between the feature and the result of the value expression." (`SysML_Spec_v2_Part1/full_document.md:5273`, `:5278`)
- Feature-value semantics is binding/equivalence, 7.13.4: "The semantics of binding mean that such a feature value asserts that a feature is _equivalent_ to the result of the value expression." (`:5293`)
- Calc parameters are directed usages, 7.19.2: "As for an action definition or usage, directed usages declared in the body of a calculation definition or usage are consider[ed] to be parameters." (`:7935`)
- Deferral of name resolution, Part 1 clause 7.5: "_Name resolution_ is the process of determining the element that is identified by a qualified name. An unqualified name used within the body of a namespace is resolved in the context of that namespace and, potentially, other namespaces in which the first namespace is lexically nested, taking into account imported ... and inherited ... memberships. ... The full name resolution process is specified in [KerML, 8.2.3.5]." (`:2721`)
- Definitions and usages are namespaces (so the calc usage's own parameter `R` is a member visible to nested resolution), 7.5: "all kinds of SysML _definitions_ and _usages_ are also namespaces ... All rules discussed generically for namespaces in this subclause 7.5 apply generically to packages, definitions and usages." (`:2705`)

RESIDUAL AMBIGUITY: Part 1 states the nearest-nested-namespace rule but delegates the tie-break/shadowing detail (whether the parameter member `R`, being an inherited/redefining member of the calc usage, outranks the enclosing part's `R`) entirely to KerML 8.2.3.5; Part 1 gives no worked example of a same-named parameter shadowing an enclosing attribute, so the "bare `R` binds to the parameter" outcome is inferred from the general nearest-scope rule, not stated verbatim in Part 1.

Q2 — Redefinition semantics of `:>> R = 12.7`; which value applies in occurrence `plant`

VERDICT: `:>> R = 12.7` creates a NEW feature that redefines `'Probe Plant'::R`; redefinition is a kind of subsetting in which the redefining feature **replaces** the redefined feature in the context of the redefining usage. The def-level `attribute R : Real default 3.0` is a **default** feature value, which is explicitly overridable by a redefinition. In the context of occurrence `plant`, the applicable value is the override **12.7**, not the default 3.0. A reference that statically resolved to `'Probe Plant'::R` still denotes, in `plant`'s context, the single R feature that the redefinition has replaced/valued at 12.7.

QUOTED NORMATIVE TEXT:
- Redefinition replaces, Part 1 clause 7.6 (Redefinition): "_Redefinition_ is a kind of subsetting. While, in general, a subsetting usage is an additional feature to the subsetted usage, a redefining usage _replaces_ the redefined usage in the context of redefining usage." and "the new redefining feature replaces the `fuel` feature that would otherwise be inherited, meaning that the `fuel` of the `truck` part must be defined by ..." (`:3232`, `:3242`)
- Default is overridable; override wins, Part 1 clause 7.13 (Bindings/Feature Values overview): "a default feature value can be overridden in a redefinition of its original feature with a new feature value (fixed or default). In this case, the new overriding feature value is used instead of the original feature value for binding the redefining usage." (`:4859`)
- Default-value application at instantiation, 7.13.4: "For a default feature value relationship, no implicit binding is added ... but the default will apply when an instance of the owning definition or usage is constructed, if no other explicit values are given for the defaulted usage." (`:5330`)

RESIDUAL AMBIGUITY: The "replaces in the context of the redefining usage" text (7.6) and the "override is used" text (7.13) both directly support 12.7 for values evaluated in `plant`'s context. What Part 1 does NOT spell out with an example is the cross-context case the probe raises: when a name is statically resolved to the general Feature `'Probe Plant'::R` (e.g., inside another part's calc), whether evaluation re-dispatches that reference to the redefining feature's value under a given occurrence is left to KerML featuring/evaluation semantics rather than stated in Part 1. The value-in-context claim (12.7 for `plant`) is firm; the behavior of an externally-held reference to the def-level symbol is not illustrated normatively in Part 1.

Q3 — Referring to attribute R of the i-th occurrence of `plants[2]`

VERDICT: Yes, there is a normative textual way, and `plants#(1).R` is (a form of) it: `#(i)` is the KerML **index expression** operator, applicable to an ordered/multiplicity->1 feature, combined with a feature chain via `.`. Indexing is 1-based over Natural/Positive. There is NO `[i]` bracket indexing form in the textual notation: after an expression, `[...]` is the (by-default undefined) bracket operator reserved for domain-specific use, which is what the quantity/units notation (e.g., `2000[kg]`) uses — it is not an index. The probe's `plants#(1).R` and the chain form `scenario.position#(i)` are the same operator; the only difference is index-then-chain vs. chain-then-index ordering.

QUOTED NORMATIVE TEXT:
- Part 1 shows the operator in an example, clause 7.17: "The `..` operator can be used to construct a sequence of Integer values ... useful ... (especially for indexing)." with example `positionList->including(scenario.postion#(i));` (`:7297`, `:7303`)
- Ordered usages are index-addressable, Part 1 clause 7.6: "If a usage is _ordered,_ then the values of the usage can be placed in order, indexed from 1 to the [number of values]." (`:3555`)
- Index operator definition (deferred KerML), KerML clause 8.2 primary expressions: "An index expression specifies the invocation of the indexing function '#' from the BaseFunctions library model ... the first operand is expected to evaluate to a sequence of values, and the second operand is expected to evaluate to an index into that sequence. Default indexing is from 1 using Natural numbers. Note that parentheses are required around the second operand." example `sensors#(activeSensorIndex)` (`SysML_KerMLSpec/full_document.md:2409`, `:2411`, `:2414`)
- Bracket `[...]` is NOT indexing, KerML clause 8.2 Note 2 + Table 7: "The grammar allows a bracket syntax [ ... ] that parses to an invocation of the library Function BaseFunctions::'[' ... no default definition is provided in the Kernel Functions Library. If no domain-specific definition is available, a tool should give a warning if this operator is used." Table 7 rows: `[  BaseFunctions::'['  Undefined  No`; `#  BaseFunctions::'#'  Indexing  Yes`. (`SysML_KerMLSpec/full_document.md:3464`, `:3472`)
- Units use the bracket operator, Part 1 example: `attribute :>> massRequired = 2000[kg];` (`SysML_Spec_v2_Part1/full_document.md:8515`)

RESIDUAL AMBIGUITY: The precise index operator, its 1-based semantics, and the `[...]` = undefined-bracket rule live in KerML 8.2, which Part 1 adopts by reference ("KerML ... expression sublanguage ... adopted in its entirety"; `SysML_Spec_v2_Part1/full_document.md:7879`) rather than restating. Part 1 itself shows `#(i)` only inside a `for`-loop example, not specifically for indexing a multiplicity-`[2]` part usage, so `plants#(1).R` is supported by the general operator definition, not by a directly analogous Part 1 example. Whether `#` applies cleanly to a composite part usage of multiplicity `[2]` (vs. an ordered attribute sequence) is governed by KerML collection/ordering semantics, not illustrated in Part 1.

Q4 — Is `in R = R;` blessed as "bind to enclosing part's attribute," or a degenerate self-reference?

VERDICT: The spec does NOT bless `in R = R;` as "bind to the enclosing part's attribute." Under the deferral to KerML nearest-scope resolution, the bare RHS `R` resolves to the nearest `R` in scope, which is the calc usage's own `in R` parameter (a member of the calc-usage namespace), producing a degenerate self-binding rather than a reference to the enclosing part's attribute. No Part 1 clause or example authorizes same-name shadowing as a bind-to-enclosing shorthand. Every same-name binding example in the spec is a redefinition of an inherited/definition-level parameter by name (which is a different mechanism), not a value expression whose RHS is a bare same name resolving outward past the parameter.

QUOTED NORMATIVE TEXT:
- Nearest-nested resolution (same as Q1), 7.5: "An unqualified name used within the body of a namespace is resolved in the context of that namespace and, potentially, other namespaces in which the first namespace is lexically nested ..." (`SysML_Spec_v2_Part1/full_document.md:2721`)
- The calc usage is itself a namespace whose parameter `R` is a member, 7.5 (`:2705`) and 7.19.2 (`:7935`) — quoted above.
- The spec's actual same-name idiom is redefinition-by-name of a parameter, not a self-valued expression, 7.19.2: "calc computation : Dynamics { // Parameters redefine parameters of Dynamics. in initialState; in time; return result; }" (`:7977`) — here `in initialState;` redefines the definition's `initialState` by matching name; it carries no `= <expr>`, so it is not the `in R = R` construct.
- Binding a parameter to an OUTER feature is shown only with a distinct path, not a bare same name, 7.24.2: `in massMeasured :> ISQ::mass = collectData.massMeasured;` (`:9150`) and 7.21: `attribute :>> massActual = vehicle.totalMass;` (`:8514`).

RESIDUAL AMBIGUITY: Part 1 never presents `in R = R;` (bare same name on both sides) as an example, so the "degenerate self-binding" reading is derived from the general resolution rule plus the feature-value=binding semantics, not from an explicit spec statement classifying this exact construct. Whether a conforming tool must resolve the RHS `R` to the parameter (self) or could resolve it to the enclosing attribute is entirely a function of KerML 8.2.3.5 shadowing precedence, which Part 1 does not reproduce or exemplify for the parameter-vs-enclosing-attribute collision. The SysIDE outcome (RHS binds to the parameter) is the reading most consistent with nearest-scope resolution, but Part 1 offers no verbatim confirmation.

Q5 — Spec-sanctioned form for "bind this calc input to the enclosing part's attribute of the same name"

VERDICT: The spec-sanctioned form is a value expression whose RHS **names the target feature by a path that does not collide with the parameter** — i.e., a qualified name or a feature chain (e.g., owner-qualified `'Probe Plant'::R`, or a feature chain rooted at a distinct feature such as `subject.mass` / `vehicle.totalMass`). The spec's own binding examples all use a distinct qualified/chained RHS, never a bare same name. There is no SysML textual `self`/`this` keyword shown in Part 1 for rooting such a chain at the enclosing occurrence; the enclosing feature is reached by naming it (qualified name) or by chaining through a named containing feature (subject, or a named part).

QUOTED NORMATIVE TEXT:
- Feature chain is the general mechanism for identifying a (possibly outer/nested) usage as a relationship target, 7.6.6: "A _feature chain_ is a textual notation specified as a sequence of two or more qualified names separated by dot ( `.` ) symbols. ... The first qualified name in a feature chain is resolved in the local namespace as usual ... Subsequent qualified names are then ... resolved using the previously resolved usage (feature) as the context namespace ..." and "when a textual notation is described as including the _identification_ of a usage, this can be done by using either a qualified name or a feature chain." (`SysML_Spec_v2_Part1/full_document.md:3699`, `:3720`)
- Blessed example of binding a parameter to an enclosing feature via a chain (requirement idiom), 7.21: "attribute :>> massActual = vehicle.totalMass;" (subject-rooted chain to the outer feature) and "attribute :>> massRequired = 2000[kg];" (`:8514`, `:8515`).
- Blessed example in a verification case, 7.24: "in massMeasured :> ISQ::mass = collectData.massMeasured;" (RHS is a feature chain to a sibling's output, not a bare name) (`:9150`).
- Case/subject binding by distinct name, 7.22 example: "subject engine = vehicle.engine;" (`:8581`).

RESIDUAL AMBIGUITY: Two open points.
(1) Part 1 gives no example of the owner-qualified form `'Probe Plant'::R` used as a calc-input RHS, so its use to reach the enclosing DEF-level attribute is inferred from the qualified-name resolution rule (7.5) plus feature-chain rule (7.6.6), not shown verbatim. The SysIDE observation that `'Probe Plant'::R` resolves to the DEF-level attribute matches the qualified-name rule.
(2) The probe's core semantic gap remains: an owner-qualified name resolves to the general/def-level Feature, whereas a feature chain rooted at the specific occurrence (e.g., `plant.R`, resolving to the redefining `:>> R = 12.7` site) reaches the redefined feature. Which of these two "same-named enclosing attribute" targets a modeler intends is a real distinction Part 1 does not adjudicate with an example; the spec supplies both mechanisms (qualified name → general feature; occurrence-rooted feature chain → redefined feature) without a normative statement picking one as THE idiom for "the enclosing part's attribute of the same name." No `self`/`this` keyword was found in Part 1 or KerML concrete syntax to root such a chain at the current occurrence.
