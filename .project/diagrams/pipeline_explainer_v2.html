sysml-codegen · interactive explainer · generation 2

From a SysML v2 model to a running simulation pipeline

A modeler describes a plant — its parts, its numbers, its calculations — in SysML v2. sysml-codegen turns that model into an executable Python pipeline: modules, schemas, input files, wiring. This page explains what the pipeline is for, how it works algorithmically, and how it is operated.

Current as of merged main (936315c, 2026-07-20) — after the PIPELINE-TRUTH, CONSTRAINT-EXEC, and CONSTRAINT-LIFECYCLE epics. Read the first two sections for the two-minute story; every deeper layer is a click, never required.

Layer 0 · two-minute read

Why this exists

Techno-economic simulation frameworks (TEAx-style) run a plant model as a set of Python modules wired together: each module computes something, its outputs feed other modules' inputs, and a pipeline definition says who runs when. Building that by hand means writing the modules, the input schemas, the JSON parameter files, and the wiring — and keeping all four consistent with the engineering model they came from.

sysml-codegen removes the hand-plumbing. The engineering model — written in SysML v2, the systems-engineering modeling language — becomes the single source. A modeler writes two kinds of things:

  • Algorithms — calculation definitions (calc def) in a library: what can be computed, from which inputs.
  • Configuration — part hierarchies with attribute values and bindings in a design: which parts exist, what their numbers are, and which calculation feeds which.

The pipeline parses that model, works out who-feeds-whom, and generates a complete package. "Done" looks like: an importable Python package with one module per calculation, implementation stencils for the parts that need handwritten math, JSON input files pre-filled with the model's values, pipeline YAML that wires it all together — and, since the constraint-execution work, the package is sealed: it carries a verifier that proves a consumer loaded exactly the bytes that were generated (→ Contracts & sealing).

The real consumer is fusion-tea, whose fusion-plant models run through this pipeline. The proof point: the full fusion-tea plant YAML generates with zero unresolved inputs, and its reference run reproduces the levelized cost of electricity bit-exactly ($270.1211779380445/MWh) through the generated package alone — no hand-written glue. Modeled assertions (like "outer radius must equal inner radius plus thickness") don't just document intent anymore; they execute as part of the run (→ Constraints execute).

The two-repo contract sysml-codegen executes a defined subset of SysML v2. Its sibling repo agentic-mbse teaches that subset (modeling guides, pattern stencils) and checks it (validation rules with negative fixtures) before generation ever runs. One document — docs/architecture/modeling-assumptions.md — says what models must look like; both repos hold to it (→ agentic-mbse, the enforcement half).

Layer 1 · the spine

The pipeline shape

The pipeline is seven steps: extract the model into typed data, resolve who-feeds-whom into a single graph, generate code from that graph. Everything deeper on this page hangs off this diagram — click a stage to jump to its responsibility, and use the module-kind graph below it to see what the output looks like.

The 7-step pipeline + the snapshot front end click a stage to jump to its section

Two facts carry most of the architecture:

  • One graph is the boundary. Steps 1–6 produce a single ComputationGraph (a Pydantic model, resolution/models.py); Step 7 reads only that graph — no back-references to extraction data (requirement REQ-PIPE-07). If generation needs a fact, the fact must live on the graph.
  • The snapshot path is a first-class front end, not a cache. sysml-codegen snapshot captures extraction output as versioned JSON (format v5), and generate --from-snapshot rebuilds the same pipeline context from it with no parser toolchain — Steps 2–7 run unchanged, and the output is byte-identical to a live run (→ Operating it).

Five module families

Every module in the graph carries a module_kind (resolution/models.py, doc 09). Three are the calc families every model produces; two exist only when the model carries constraints:

CALCULATION — a calc usage FORMULA — a computed attribute AGGREGATION — a sum-over-children roll-up CONSTRAINT — a lowered assertion REPORT_AGGREGATOR — the run-report roll-up

Layer 2 · who owns what

Every mechanism, its responsibility, and the problem that forced it

Nothing in this pipeline exists for elegance. Each module earns its place by answering a specific failure that real models produced. The table pairs each owner with its one-sentence responsibility and that forcing challenge. Click any row's owner link where a deeper treatment exists.

OwnerTight responsibilityThe challenge it answers
extraction/extractor.py Pull calc defs and usages with typed inputs/outputs out of the parsed AST (→ the AST layer). SysML lets one output be spelled several ways (out attribute, return x : Real =, bare in parameters alongside); an anonymous return has no name to build a channel from — that is diagnostic V8.
extraction/usage_extractor.py Turn template calcs (a calc inside a part def) into per-instance virtual calc usages (→ virtual instantiation). extraction/hierarchy_resolver.py Capture the design hierarchy plus every :>> override, multiplicity, and aggregation expression. Values live scattered across usage overrides, specialized defs, and base defs — someone has to collect them all before resolution can pick a winner.
extraction/computed_attribute_extractor.py Classify each design-attribute expression: FORMULA, EXPOSE_PURE, chain-tentative, literal, rejected, or unresolvable (→ classification tree). An attribute expression can be an algorithm, an alias for a calc output, or a config value — and each takes a completely different path through the pipeline.
core/output_registry.py + orchestration/output_registry_builder.py One authoritative name→channel registry with typed keys and a phased build, including the Phase 3b multi-hop confirm walk (→ the registry). Ambiguous string keys caused silent mis-wires; and a multi-hop chain can't be classified at extraction because the leaf can't be checked without the registry that doesn't exist yet.
analysis/dependency_backtracker.py Resolve every calc-usage binding to exactly one source via typed dispatch ladders (→ dispatch). Quoted names, def-owned attributes, sibling instances of one type, and cross-part chains all spell the same value differently; a wrong guess wires the wrong producer.
resolution/producer_resolution.py + resolution/producer_completeness.py One registry-owned ordered resolution table (resolve_producer, KEY_FORMS) serving calc, aggregation, and constraint consumers alike — strict vs lenient behavior forks only at the terminal miss (TerminalPolicy); a separate completeness check proves every model-derived consumed value has a real producer (→ the unified ladder). Three drifted resolver ladders let the same meaning resolve three ways — a passing component test could still mis-resolve a supported combination. The lifecycle epic collapsed them into one authority and deleted input_resolver.py outright.
resolution/supplied_values.py Pre-pass that materializes design attributes for cross-part and in-part supplied values, keyed by source qualified name, before the backtracker runs (→ supplied values). A literal sitting on a subsystem attribute must fill a plant-calc input, or generation aborts at V11 — the whole-plant idiom fusion-tea depends on. Fan-out collapses to one shared entry point per source.
orchestration/pipeline_builder.py Ordered assembly: rewrite virtual bindings through the specialization chain (usage override > specialized-def :>> > base def), then backtrack, then derive groups. Step order is the correctness argument — classify entry points before the binding rewrite and a design value reads as an unbound library default.
resolution/graph_builder.py Emit the ComputationGraph — the sole input to generation — and gate it (V11 params-coverage, channel validation) (→ the V11 gate). A generated pipeline that KeyErrors at load is worse than a loud abort at generation time.
analysis/parameter_groups.py Turn entry points into per-design-file JSON input groups. Deciding which literals are user-facing knobs: LIBRARY_DEFAULT, DESIGN_ATTRIBUTE, or USAGE_LITERAL (ADR-001).
generation/ Render the graph into wrappers, stencils, schemas, and YAML; apply alias filename overrides; smart-regen preserves handwritten implementations. Generated code that people edit must survive regeneration, and the modeler's chosen names must surface in the output files.
snapshot/ Versioned extraction capture (now v5); an old snapshot is a hard error, and regeneration from a current one is byte-identical to live (→ operations). Generation, debugging, and CI shouldn't require the live parser toolchain on every run.
analysis/constraint_lowering.py Lower each eligible modeled assertion to a concrete constraint — strict formal resolution per owner instance; default-on (→ constraints). A modeled assert used to be dropped. It now executes, so the value it checks must resolve exactly like any calc input.
resolution/models.py (ModuleKind) Tag every module with one of five families: CALCULATION, FORMULA, AGGREGATION, CONSTRAINT, REPORT_AGGREGATOR. Two accreted boolean flags could not name the constraint and report-roll-up families; one enum, set once, dispatched on at every generation seam.
generation/constraint_catalog.py Assemble one fingerprinted catalog (source records + concrete entries), embedded on the ComputationGraph, read only from the graph at generation. Generation must read constraint data from the single-source-of-truth graph, never from mutable pipeline context.
generation/predicate_compiler.py Compile each predicate's expression IR to Python under three-valued (Kleene) semantics; one shared predicates module, compiled once (→ Kleene predicates). A non-finite leaf must make a predicate unknown, not silently False — a lying gate is worse than a loud one.
generation/errors.py render seams Render CONSTRAINT / REPORT_AGGREGATOR modules at their own seams; a seam with no rendering for a kind fails loud (unrenderable_module_kind_error). Every module kind must render or refuse — never be silently mis-rendered as a calculation.
contracts/ Emit the semantic ModelContract, the physical PackageContract seal, a verbatim verifier, and a generation manifest; the seal CLI re-seals in place (→ sealing). A consumer must confirm it loads exactly the bytes generated, know what it may vary without parsing YAML, and never execute a package that forged its own verifier.
teax simkit/study/ The top-of-stack consumer: load a generated+sealed package, obtain typed entry models, drive many cases through an evaluator (→ the study layer). The generated pipeline is a means; a study sweeping designs over it is the end the whole stack serves.

The user-facing surface

Diagnostics as contract

Every internal invariant in this pipeline has a user-facing surface: the message a modeler sees when an assumption breaks. Three surfaces exist, at three moments — model-shape rules at extraction and generation (V1–V11), a severity contract deciding which extraction diagnostics halt, and a load-time seal check on the generated package. Read them as one system: the pipeline would rather stop loudly than generate something that lies.

V1–V11: what the modeler sees when an assumption breaks

V1–V10 fire at extraction time; V11 fires at the generation boundary, where the computation graph and the derived parameter groups both exist (docs/architecture/modeling-assumptions.md, "Validation Rules").

RuleThe broken assumptionWhere it fires
V1A calc def in designs/ — algorithms belong in library/.Extraction
V2An expression that can't be statically evaluated (an operand isn't a literal) — extract it to a calc def.Extraction
V3A circular reference between values.Extraction
V4An unsupported operator in a static expression.Extraction
V5An unbound calc input with no default — add a default or a binding.Extraction
V6A binding to an attribute that doesn't exist.Extraction
V7A calc def with zero output attributes — a pipeline module needs at least one output channel.Extraction
V8An anonymous return (a result with no name) — no channel name can be built from it.Extraction
V9Two template calcs from different owners (a retyped usage's super- and subtype) collide on one virtual name — the most-specific owner wins, and the warning names both.Extraction
V10A usage with multiple incomparable owned types — defaults resolve against the first in stable order, loudly.Extraction
V11A wired module input references a params key no JSON input file will provide — the generated pipeline would KeyError at load, so generation aborts instead, naming every offender (→ the exact set logic).Generation boundary

There is deliberately no V12/V13: the cross-part mechanisms added later are positive resolution — they wire channels that used to fall through — so a model that still fails to wire surfaces through the existing V11, not through a new code.

The severity contract: which diagnostics halt

Not every extraction diagnostic should stop the run. The severity contract (doc 30, analysis/diagnostic_screen.py) is how the pipeline decides a broken assumption is fatal rather than noise — and it is versioned, so a reader and writer can never silently disagree:

  • The writer sets severity at construction, from a closed table. Each extraction diagnostic carries a DiagnosticSeverity — BLOCKING or ADVISORY — filled in when the diagnostic is created, from the one kind→severity table (EXTRACTION_DIAGNOSTIC_SEVERITY, in agentic-mbse's constraint_facts module). No reader ever looks severity up on its own.
  • One sink screens them. screen_extraction_diagnostics runs on both the live and the snapshot route, before constraint lowering. It renders every advisory first (as warnings), then raises on any blocking diagnostic, naming all of them. The order is enforced so a failure while rendering an advisory can never mask a block.
  • Skew fails closed, in both directions, behind three stacked guards: an exact-equality schema-version gate (constraint-facts/v2, pinned in _upstream_pins.py); a per-diagnostic cross-check that re-derives severity from the reader's table and refuses a mismatch either way; and a refusal of any diagnostic kind outside the closed set.

The executable profile: which assertions may run

Modeled constraints get their own contract, evaluated in agentic-mbse (evaluate_profile, executable_profile.py): every swept constraint usage is classified exactly one way — ADMIT (it lowers and executes), BLOCK (generation halts loudly before any lowering, naming every offending usage and the construct to fix), or unassessed (requirement-side or out-of-profile usages, cataloged defensively — never silently absent). A BLOCK is the one hard-stop: an assertion the profile cannot execute exactly is refused, never approximated. Full treatment in the constraint path.

Sealing: the load-time contract

The third surface guards the far end: when a consumer loads the generated package, the emitted verify.py re-hashes every covered file against the package's PackageContract and reports TAMPER, MISSING, EXTRA, or a name mismatch — always fatal — and a runtime-version mismatch, advisory unless strict. A ModelContract fingerprint is the package's semantic identity. This is how a consumer knows it loaded exactly what was generated (→ Contracts & sealing).

One value, end to end

A worked example: annual_energy_mwh from source to YAML

Everything abstract above becomes concrete on one value. In the committed solar-battery fixture (tests/fixtures/solar_battery_model/, 36 pipeline modules), the energy-production calc computes annual energy, and the LCOE calc consumes it. 1 · The SysML source

2 · What the parser sees (the AST)

The extractor never works on text — it dispatches on the parsed node kinds (→ the AST layer for the full taxonomy):

  • The output declaration is an AttributeUsage (direction Out); its : Real is a FeatureTyping to ScalarValues::Real. Its right-hand side is an OperatorExpression (*) over three FeatureReferenceExpression nodes and one LiteralRational (8760.0) — stored raw for the expression compiler, which auto-implements the module body.
  • The binding's right-hand side energy_production.annual_energy_mwh is a FeatureChainExpression — a dotted path. The extractor classifies the binding CHAIN. The check for FeatureChainExpression runs before the OperatorExpression check, because FCE is a subtype of OE in the parser's type hierarchy (→ the dispatch invariant).

4 · The registry entry and the resolved binding

Step 2 registers the producer's output under typed keys: the canonical channel above, plus a hierarchy-scoped key (solar_battery_plant.energy_production.annual_energy_mwh) that is unique by SysML ownership. When the backtracker meets the consumer's CHAIN binding, it prepends the consumer's scope to the source path — solar_battery_plant + energy_production.annual_energy_mwh — and the scoped lookup lands on exactly that key. Result: a MODULE_OUTPUT resolution carrying the canonical channel. No string guessing; ambiguity is impossible by construction because unscoped names are never registered (→ the registry).

Layer 3 · the algorithms

The mechanisms

Six mechanisms do most of the pipeline's real work. Each subsection leads with what the mechanism is for, then how it works; each links back to where it sits in the pipeline.

Virtual CalcUsage instantiation Step 1 → 3.5

A calc written inside a part def is a stencil for every instance of that part — not an instance itself. Extraction detects these templates (their owner is a part definition), and for each design part usage of that definition it spawns a virtual calc usage whose qualified name is the full design path (usage_extractor.py, docs 12/25). Ten solar-panel instances of one part def become ten virtual calcs, each with its own copies of the template's bindings.

The virtual copy's generic bindings are then rewritten per instance (_rewrite_virtual_bindings, orchestration/pipeline_builder.py): an override index keyed by (parent path, leaf attribute) maps each design :>> redefinition onto the matching binding — a LITERAL override makes the binding a literal, a CHAIN override redirects its source path. Bindings are copied per instance, so no two instances share mutable state. Retyping (part :>> driver : 'HIF Driver') indexes the usage under every user-model type it carries, so subtype and supertype templates instantiate — a same-named collision resolves to the most-specific owner with a V9 warning (→ the retyping snippet).

The assembly ordering argument Steps 1–6

build_pipeline_context() (doc 02) is a fixed sequence, and the sequence is the correctness argument — reordering produces wrong answers, not crashes:

  • 3.5 before 4: virtual bindings are rewritten (mutated in place) before design attributes are read — otherwise a design's :>> wattage = 400.0 reads as an unbound template input and classifies LIBRARY_DEFAULT instead of DESIGN_ATTRIBUTE.
  • 4.5 before 5.7: FORMULA attributes are removed from design attributes before the parameter-group deriver runs — otherwise a computed attribute mints a false entry point.
  • 5.5 before 6: the registry (including its Phase 3b confirm walk) is final before the backtracker resolves anything, and re-running FORMULA removal at 5.6 covers the case where a Phase-3b revert re-introduced a FORMULA.
  • 5.65 before 6: the supplied-value materializer enriches design attributes before the backtracker, so cross-part literals are visible to resolution (→ supplied values).
  • [P1 RESOLVE] after 5.65: constraint lowering runs once the registry and materialized values are final — a constraint formal resolves against the same world calc inputs do (→ constraints).

The output registry: one name→channel authority Step 2 / 5.5

The problem: SysML spells the same output several ways depending on context. A dotted local path (cost_model.total_cost), a hierarchy path from a redefinition, a ::-qualified name from a reference — different strings, one value. Early versions used ad-hoc string keys and paid in silent mis-wires.

The registry (core/output_registry.py, doc 10) answers with typed keys: four sub-registries, each keyed by a distinct NewType, all mapping to one CanonicalChannel:

Key typeShapeAnswers
ScopedKeysolar_battery_plant.energy_production.annual_energy_mwhDotted hierarchy paths — unique by SysML ownership, matchable from the consumer's scope
SysMLQNSolarBatteryLibrary::EnergyProductionCalc::annual_energy_mwh::-qualified REFERENCE bindings
ScopedKey (alias registry)battery_pack.capital_cost → canonicalCHAIN redefinitions, EXPOSE aliases, transitive design-attribute aliases
ScopedAliasKey(instance_path, leaf_name) — a tuple, not a stringPart-def EXPOSE names, expanded per instance; the tuple keeps ("a.b","c") and ("a","b.c") distinct by construction

The build is phased (orchestration/output_registry_builder.py): Phases 1a/1b/1c register canonical channels (calc-usage outputs, aggregation outputs, FORMULA outputs); Phases 2/3/4 register aliases (CHAIN redefinitions, EXPOSE_PURE, transitive design attributes) — and register_alias refuses a target channel that doesn't already exist, so out-of-order registration is impossible. Unscoped bare names are never registered at all: ambiguity is prevented by construction, not detected after the fact.

Phase 3b: the multi-hop confirm walk

A multi-hop chain like tf_coil.volume_calc.volume can't be classified at extraction: whether the leaf is a calc output is unknowable without the registry, which doesn't exist yet. So extraction tags it EXPOSE_CHAIN_TENTATIVE and the registry build finishes the job in Phase 3b: walk the chain against the now-populated registry; if it lands on a canonical channel, finalize to EXPOSE_PURE and register the real transitive alias; if not, revert to FORMULA treatment. An invariant (INV-F) raises if any tentative survives to a reader — downstream code never sees the intermediate state. The walk is reconstructed on snapshot load, so offline and live runs wire the identical channel.

The backtracker: resolution embedded in traversal Step 3

Starting from the root calc usages, the backtracker (analysis/dependency_backtracker.py, docs 11/24) walks depth-first through bindings. At each binding it must decide: does this input come from an upstream module (recurse into the producer) or from outside (stop — it's an entry point)? Resolution can't be separated from traversal, because the resolution result is the recurse-or-stop decision.

Dispatch is type-directed on the binding's source path — the presence of :: splits two ladders:

For energy_production.annual_energy_mwh-style paths:

  1. Consumer-scope-prefixed scoped_lookup — prepend the consumer's scope, look up the scoped key.
  2. Bare scoped_lookup — the FORMULA owning_part.attr shape.
  3. scoped_alias_lookup — the part-def EXPOSE namespace, consumer-scope-prefixed first then bare (sibling disambiguation, REQ-BT-11 → scoped aliases).
  4. alias_lookup — cross-package aliases.
  5. Design-attribute match — the value is configuration, not a module output.
  6. Fallback: mint an entry point, recorded as fell-through (feeds the V11 partition below).

For Package::Calc::output-style qualified names:

  1. sysml_qn_lookup on the per-segment sanitized qualified name — so quoted owners like 'PV Module' still match.
  2. Leaf-plus-scope retry: the leaf name qualified by the consumer's parent part, then the full consumer scope, through scoped-then-alias lookups — this is how a design attribute owned by a part def (empty parent part) still resolves.
  3. Design-attribute match.
  4. Fallback entry point (fell-through).

Every hit passes a self-reference guard — a module is never wired to its own output — and each resolved binding lands in BacktrackingResult.binding_resolutions, exactly one source per binding (REQ-PIPE-02).

One resolution authority: resolve_producer Step 5 · unified by CONSTRAINT-LIFECYCLE

The backtracker resolves calc-usage bindings during DFS — but FORMULA inputs, aggregation inputs, and (since constraint execution) constraint formals also need resolving, outside any traversal. For years those paths carried their own resolver ladders, and the three ladders drifted: the same reference could resolve three different ways, and a passing component test could still mis-resolve a supported combination. The lifecycle epic collapsed them.

resolve_producer (resolution/producer_resolution.py, doc 04) is now the single registry-owned authority: one ordered table of 21 key forms (KEY_FORMS), partitioned into two tiers, serving calc, aggregation, and constraint consumers alike. The old input_resolver.py — with resolve_input and its AGG_STRATEGIES — was deleted, not wrapped.

Strict and lenient consumers walk the same table; behavior forks only at the terminal miss (TerminalPolicy): a calc or aggregation input (lenient) mints one entry point and moves on; a constraint formal (strict) raises a contextual error rather than inventing a value — a constraint that can't find its operand must not guess (INV-2).

Alongside sits a separate proof: check_producer_completeness (resolution/producer_completeness.py) re-reads every resolution and flags ambiguous producers (same-leaf ties) and leaf-name guesses (a qualified reference that dropped its scope through a name-based row) — independent of V11, as a diagnostic rather than a gate.

Computed-attribute classification Step 4.5

A design attribute with an expression can be three different things, and each takes a different pipeline path: an algorithm (area = length * width → a FORMULA module), an alias (total = cost_calc.cost → an EXPOSE channel alias), or a config value (a literal → an entry point). The classifier (extraction/computed_attribute_extractor.py, doc 16) decides by examining the expression's references:

  • No references → literal (entry-point path).
  • Only sibling attributes (including inherited ones, via a transitive ancestor walk) → FORMULA — unless the expression is a single well-formed multi-hop chain, which becomes EXPOSE_CHAIN_TENTATIVE for Phase 3b to settle.
  • A single pure dotted reference to a calc output → EXPOSE_PURE (the alias).
  • A calc-output reference mixed with anything else (e.g. scale_calc.result * 2.0) → EXPOSE_COMPUTED — rejected; it produces no module and no alias, with a warning. Model it as a calc def instead.
  • An unresolvable reference → UNRESOLVABLE (diagnostic).

The V11 gate: no silent KeyErrors Generation boundary

The last line of defense before rendering. collect_uncovered_params (resolution/graph_builder.py) computes a three-way intersection — a module input is an offender if and only if its entry point:

fell through resolution (Step-4 fallback)  ∩  carries no value (no default)  ∩  is still wired (a surviving module reads it)

Any offender aborts generation with every one named — because the generated JSON would never mint that key, and the pipeline would KeyError at load. The other halves of the partition stay legitimate: a fell-through entry point with a value is fine, and a null-default entry point that did not fall through is the normal "user fills this in" signature. The unwired half of fell-through-valueless is a warning summary, not an abort. The supplied-value materializer is what took fusion-tea's V11 offender count to zero (→ supplied values).

Alias surfacing: the modeler's name reaches the output Steps 6–7

When a modeler exposes a calc output under a chosen name (attribute total_cost : Real = cost_calc.cost;), that name used to vanish into the canonical channel. Now it travels: ComputationGraph.output_aliases carries one OutputAlias per surfaced name — the sanitized alias_name, the canonical_channel it rides on, the qualifying instance_path, and which EXPOSE shape produced it. In the pipeline YAML, the alias overrides the exit-point output filename: {instance_path}__{alias_name}.json (instance-qualified so two instances exposing the same name never collide). The exit key stays the canonical channel.

A deliberate contrast in the data model: output_aliases is a serialized field — it survives into snapshots and downstream consumers — while fallback_entry_points (the V11 bookkeeping set) is marked in-memory only (exclude=True). What a consumer needs persists; generation-boundary scaffolding does not.

The whole-plant idiom · PIPELINE-TRUTH's centerpiece

The cross-part story

A real plant model is not one flat part. fusion-tea's models are a hierarchy — driver, chamber, target factory — where a plant-level calculation needs values and outputs that live on subsystems it does not own. Supporting that took two complementary halves: channel wiring (an output of one calc reaches another calc's input, across part boundaries) and value resolution (a literal sitting on a subsystem attribute fills a plant-calc input). Together they are why fusion-tea's full YAML now generates with zero V11 offenders.

Half one: channel wiring

Four shapes cover the wiring, each with its own mechanism:

Multi-hop EXPOSE

An attribute reaches through a nested part to a calc output — attribute magnet_volume_total : Real = tf_coil.volume_calc.volume; (fixture tests/fixtures/ife_plant/subsystems.sysml). Extraction can't tell whether the chain lands on a calc output, so it classifies tentatively (EXPOSE_CHAIN_TENTATIVE) and the registry's Phase 3b confirm walk settles it: resolve transitively → an EXPOSE alias of the real channel; fail → revert to FORMULA. The walk is reconstructed on snapshot load, so the offline path wires the identical channel.

Part-def EXPOSE, expanded per instance (shape A)

When the exposing attribute lives on a part def rather than a part usage, there are no instances at extraction time — so the alias expands later, once per design instance, into a structured namespace keyed by ScopedAliasKey: a (instance path, leaf name) tuple, not a concatenated string (core/identifier_types.py). Two sibling instances of the same type each get their own key, so consumers of sibling_a.total_cost and sibling_b.total_cost resolve to different channels — sibling disambiguation by construction. The backtracker reads the namespace by splitting the consumer's source path at the last dot, with the consumer's scope prepended first (REQ-BT-11).

Specialized-def :>> chains — the gamma → lcoe shape

A consumer calc declared on a base def can consume a channel supplied by a subtype: the driver base def declares cost_per_joule; the retyped subtype supplies it via :>> cost_per_joule = meier_cost.gamma; (fixture tests/fixtures/spec_chain_channel/library.sysml); the plant's LCOE calc reads driver.cost_per_joule. _rewrite_specialized_chain (orchestration/pipeline_builder.py) rewrites the binding through the retyped part's specialized-def chain — single- and two-level (an instance-aware type-select handles a retype declared on a part usage rather than a def). Precedence is fixed: usage override > specialized-def :>> > base def (REQ-VBR-10/11).

Alias surfacing

The wiring story ends at the output directory: the modeler's exposed name becomes the exit-point filename ({instance_path}__{alias_name}.json) via ComputationGraph.output_aliases — serialized, unlike the in-memory fallback_entry_points (→ alias surfacing).

Half two: value resolution — the supplied-value materializer

Wiring moves computed values. But the commonest cross-part need is humbler: a plant calc input should be filled by a literal that sits on a subsystem attribute. Before PIPELINE-TRUTH, those references fell through resolution valueless and generation aborted at V11 — ten offenders in fusion-tea's model. The fix is a pre-pass, not a resolver change: the supplied-value materializer (resolution/supplied_values.py, REQ-SVM-01..04) runs before the backtracker and synthesizes design attributes for supplied values, keyed by the source attribute's qualified name, merged into the design-attribute pool the resolvers already consult.

Four value-provision shapes are covered:

ShapeThe model writesWhat happens
(a) subtype-def literal through a usage-level retype part :>> driver : 'Hif Driver' where the subtype def carries efficiency = 0.35 The subtype's literal materializes for the plant calc reading driver.efficiency
(b) bare no-retype override block part :>> target_factory { :>> cost_per_target = 10.0; } The override literal materializes — flat form only; see the caveat below
(c) one-hop cross-part attribute with a dotted usage override :>> chamber.cost_per_unit = 7.0 The dotted override's literal materializes under the source attribute's QN
(d) in-part supplied value in flow_rate = throughput with :>> throughput = 8.0 below it The same-def redefinition fills the binding
  • Precedence: usage override > specialized-def :>> > base def — the same rule the wiring half uses (REQ-VBR-10).
  • Fan-out collapses by source: one subsystem attribute feeding three differently-named plant inputs becomes one shared entry point (keyed by the source QN), not three JSON keys.
  • Only literals apply: a non-literal supplied value falls through to the V11 diagnostic with a warning — never silently. A real design attribute always beats a synthetic one.
The one honest exception — shape (b), nested When the part :>> override block sits on a usage nested inside an instantiated part def, capture is definition-relative while demand is occurrence-relative, and the literal is lost ([NESTED-OCCURRENCE-OVERRIDE] — see Honest caveats). The flat and array deep-path shapes capture correctly.

This is what retired the V11 ten-offender abort: fusion-tea's full YAML emits with zero offenders, its upstream workarounds were deleted, and the reference run reproduces bit-exactly (→ the study layer).

Constraints execute

A modeler can attach assertions to the model — a physical-consistency check, a plausibility bound. Before the constraint-execution epic those were dropped: reported loudly, but never run. They now lower into real pipeline modules and execute with the rest of the graph. This section traces one assertion from source to execution, using the committed wi014_toy fixture throughout.

SysML v2 — the asserting usage (an AssertConstraintUsage node)tests/fixtures/wi014_toy/toy_plant.sysml

2 · Admission: the executable profile

Before anything lowers, agentic-mbse's executable profile classifies the usage (→ the profile contract): ADMIT and it lowers; BLOCK and generation halts loudly, naming the construct to fix (an invocation, an xor/implies, a real-valued == with no tolerance band, a unit mismatch…); anything requirement-side or out-of-profile is cataloged unassessed — recorded, never executed, never silently absent. affordable is an inequality over two resolvable Reals: admitted.

3 · Lowering: formals resolve like calc inputs

Lowering ([P1 RESOLVE], analysis/constraint_lowering.py, doc 28) runs after the registry and the supplied-value materializer are final, and resolves every formal per owner instance through the same unified table calc inputs use — resolve_producer with the strict terminal policy: an unresolved formal fails contextually rather than inventing a value (→ the unified ladder). Here cost resolves to the cost_calc output channel and budget to the plant_budget design attribute. The admitted usage becomes a concrete constraint (ConcreteConstraint, resolution/models.py): a deterministic constraint_id, the owner instance path, the serialized predicate IR, polarity, and its own evaluation_channel — the verdict is a real output channel like any other.

4 · The catalog: one fingerprinted authority

All concrete constraints, their source definitions, admitted-usage records, and explicit exclusions assemble into one ConstraintCatalog (generation/constraint_catalog.py), fingerprinted (SHA-256 over canonical JSON) and embedded on the ComputationGraph. Generation reads constraint data only from the graph — never from mutable pipeline context. The catalog is embedded as the sole schema authority (catalog schema 2.0.0, contracts/versions.py): TEAx consumes the embedded catalog directly and fails closed on a version it does not accept, before reading any field. A standalone constraint_catalog.json export is out of scope by owner decision — the embedded catalog is the authority, not a temporary state (→ caveats).

5 · Predicate compilation: three-valued, never a lying gate

Each predicate's expression IR compiles to Python (generation/predicate_compiler.py) under Kleene three-valued semantics: a verdict is true, false, or unknown (Python None). The hard part is the leaves: if an operand is NaN or infinite, IEEE comparison would quietly answer False — and a gate that says "violated" when it means "I couldn't evaluate" is a lying gate. So every leaf comparison is guarded: 

def _fin(x):
    return isinstance(x, (int, float)) and math.isfinite(x)

def _cmp(op, a, b):
    """Leaf comparison: unknown (None) if either operand is non-finite."""
    if not _fin(a) or not _fin(b):
        return None
    if op == "<=": return a <= b
    ...
The emitted Kleene runtime (excerpt) — every predicates module embeds it oncesrc/sysml_codegen/generation/predicate_compiler.py

The affordable predicate compiles to a body of _cmp('<=', cost, budget), and its margin expression carries the same guard: (_norm0((budget - cost)) if (_fin(budget) and _fin(cost)) else None). Connectives propagate unknown unless a definite value short-circuits (true or unknown → true; false and unknown → false; not unknown → unknown). This is a deliberate divergence from IEEE: inf <= 1.0 is False in IEEE, unknown here. Equality never reaches the compiler — the profile refuses real-valued == upstream (model a tolerance band as two inequalities instead), and the compiler raises if one slips through.

6 · Two new module families

The graph gains CONSTRAINT modules — one per concrete constraint, all sharing one compiled predicates module (modules/constraints/predicates.py, compiled once from the catalog) — and one REPORT_AGGREGATOR module, the run-report roll-up that gathers every constraint evaluation into a ConstraintReport and embeds the catalog fingerprint. Both render at their own generation seams; a seam with no rendering for a kind refuses loudly (unrenderable_module_kind_error, generation/errors.py) rather than mis-rendering it as a calculation. A constraint-free model produces neither family and a byte-identical graph — which is why the constraint work landed without disturbing any existing baseline.

Package integrity

Contracts & sealing

A generated package leaves home. The contracts layer (contracts/, doc 29) is how a consumer, months later, knows three things: this is semantically the package I think it is, these are exactly the bytes that were generated, and nothing I run to check that is itself untrusted.

  • Semantic identity — ModelContract. Built purely from the ComputationGraph: every parameter, every output, the embedded constraint catalog (explicitly null when constraint-free), the evaluation-semantics tag ("kleene-three-valued"), and a semantic_fingerprint over the whole payload. A consumer learns what it may vary and observe without parsing YAML.
  • Physical identity — PackageContract. The seal: a SHA-256 per covered file plus one executable fingerprint over the sorted hash list, with the coverage policy recorded in the seal itself. Emitted as generation Step 9; the seal CLI subcommand re-seals an edited-by-policy package in place, with no model or parser needed.
  • The verifier travels verbatim. Every package carries contracts/verify.py — stdlib-only, byte-identical to the canonical copy in the generator. It re-hashes the package and reports TAMPER / MISSING / EXTRA / name mismatch (always fatal) and a runtime-version mismatch (advisory unless strict).
  • Trust is runtime-owned. The runtime (teax) vendors one constant — the SHA-256 of the canonical verifier (TRUSTED_VERIFIER_SHA256, contracts/versions.py) — hashes the package's verify.py against it, and only then imports it. No untrusted package code runs before the package is verified; a package cannot forge its own verifier.
  • Provenance survives re-sealing. A generation manifest (contracts/manifest.py) classifies every covered file as codegen-produced, preserved-handwritten, or runtime; check_reseal_provenance authenticates the manifest against the prior seal and refuses a re-seal that would launder a foreign or edited generated file into codegen provenance.

The dispatch ordering invariant: FCE before OE, no exceptions

In the parser's type hierarchy, FeatureChainExpression is a subtype of OperatorExpression — an instance check for OE matches both. So every site that handles both must check FCE first (doc 19, REQ-AST-01/02). Get it backwards and pv_module.capital_cost enters the OE handler, recurses to the bare capital_cost, and misclassifies as a local sibling term instead of a dotted child reference — breaking aggregation wiring quietly. The canonical order: FCE → OE → FRE → literals → the invocation catch-all last (every node carries a derived .function, so a catch-all placed earlier swallows literals). A conformance test inventories every dual-check site so a new one can't skip the rule.

Operational reality

Operating it

Two front ends, one pipeline. You run it one of two ways:

# Live extraction — parses the .sysml sources directly
sysml-codegen generate --models path/to/models --output out/ --package-name my_package

# Snapshot capture (the only step that needs the live parser toolchain),
# then generation from the captured JSON — mutually exclusive with --models
sysml-codegen snapshot --models path/to/models --output extraction_snapshot.json
sysml-codegen generate --from-snapshot extraction_snapshot.json --output out/ --package-name my_package

# Re-seal an already-generated package in place (e.g. after a policy-allowed edit)
sysml-codegen seal path/to/package --package-name my_package
CLI surface (argparse; --models / --from-snapshot are a required mutually-exclusive pair)src/sysml_codegen/cli/__init__.py
  • Snapshot format v5, hard-gated. A snapshot records snapshot_format_version; any version other than the current 5 is a hard error — no coexistence, no in-place migration; re-capture and move on. The version history is short and honest: v3 added the constraint sections (constraint_facts, part_occurrences, constraint_lowering_mode) so the offline path re-lowers constraints; v4 added the diagnostic-severity field; v5 replaced the snapshot-relative source_file with a portable root-N/<relpath> referent, so a snapshot is byte-stable across checkout roots.
  • Offline equals live, to the byte. Generation from a current snapshot is byte-identical to live generation (REQ-SNAP-19) — the confirm walk, the scoped-alias expansion, and constraint lowering are all reconstructed on load.
  • Staleness warns, doesn't block. Each snapshot records a hash of its source files; if the on-disk sources have drifted, generation warns per file plus a summary and continues — you're told you're generating from yesterday's model, not stopped.
  • Baselines regenerate only through the capture scripts, with reviewed diffs. scripts/capture_extraction_snapshots.py runs live extraction; the other two — capture_pipeline_baselines.py and capture_baseline_yaml.py — regenerate graph and YAML baselines from the committed snapshots, so both render from the same graph and cannot disagree.

The complement

agentic-mbse: the enforcement half of the contract

sysml-codegen can assume the patterns it assumes because a second repo makes sure models follow them before generation runs. The split: docs/architecture/modeling-assumptions.md says what models must look like; sysml-codegen executes that subset; agentic-mbse teaches it and checks it.

Teaching

A MODELING_GUIDE anchors the conventions — definitions in library/ ('Title Case'), usages in designs/ (snake_case), the EXPOSE pattern, the calc-architecture rule (ADR-002: algorithms in the library, values and wiring in designs). Pattern docs cover the plant idiom (the cross-part shapes this page's centerpiece section describes, each cross-referenced to a sysml-codegen fixture), and the sysml-conventions skill ships copy-paste stencils for the four core constructs so generated-by-agent models start canonical.

Checking

A six-level validation pyramid (syntax → structure → dataflow → constraints → traceability → architecture/pipeline-readiness) runs against the model, with negative fixtures pinning each check. Three examples that map straight onto codegen's failure modes:

CheckVerdictThe codegen failure it pre-empts
Self-named binding (in x = x with nothing named x in scope) FAIL A true dead-end binding; note the check is precise — in x = x covered by a same-named attribute is a supported shape, and the plant idiom uses it freely
attribute :>> attr = <expression> (the AttributeUsage redefinition form) WARN Codegen silently drops it at extraction (→ the trap) — the validator is the only voice that names it
A calc-bearing part def that no usage instantiates (plainly or by retype) FAIL Its template calcs would silently vanish from the pipeline

The executable constraint profile also lives here (evaluate_profile) — the ADMIT/BLOCK/unassessed decision the constraint path consumes.

Staying in sync

Drift between the repos is caught by an instrument, not a habit: sysml-codegen pins the upstream schema and profile versions (_upstream_pins.py — constraint-facts, expression-IR, and profile semantic versions) and a conformance test compares each pin against the value actually imported from the installed agentic-mbse, failing with an explicit "review downstream, then update the pin" message. Every epic item that changed what codegen accepts recorded a matching agentic-mbse teaching/checking update, so the contract's two halves move together.

Top of the stack

The teax study layer: what all of this is for

The generated, sealed package is not the end. It is what a study drives: sweep many candidate designs through the same pipeline, keep the evidence, find the boundary. teax's simkit (its docs/evaluation-and-study.md) closes the loop:

  • Load, verifying the seal first. The loader authenticates the package's own contracts/verify.py against the vendored trust anchor, runs it, and refuses a package that fails integrity (→ sealing). No untrusted package code executes before that.
  • Typed entries, from the package's own truth. PreparedEvaluator.entry_models exposes a channel → typed-model map — one Pydantic model class per entry channel, derived from the pipeline spec, never a hardcoded generated class name. The stock multi-entry bridge (CandidateBridge, lifecycle Item 9) builds one complete typed model per channel — a candidate's selected fields applied over each channel's modeled defaults — for zero, one, or many entry channels, with no per-consumer wrapper. An unknown field or a malformed value fails closed as an entry-validation defect.
  • Evaluate, then study. A prepared evaluator runs one case in memory (fresh execution context per case) and yields an immutable evidence record: outputs, constraint verdicts (satisfied / violated / indeterminate — the Kleene third value survives to the top of the stack), and provenance (executable fingerprint, input digest). A study definition — a candidate strategy, a validation step, an assessment policy — drives many cases through a crash-safe store (SQLite WAL, staged-then-committed, single-runner lease).

The acceptance anchors that certified this whole stack, recorded in the epic close-outs (.project/completed/): fusion-tea's run-C LCOE reproduces bit-exactly ($270.1211779380445/MWh) through the generated package alone; the stellarator demo's five constraint verdicts land with six bit-exact anchors; and the IFE model sweeps a 2,301-point (η×G) grid through the stock seams with unchanged numerics — the composed 41/41 public proof at the pinned artifact set.

That is the frame to leave with: sysml-codegen is the means — the study sweeping designs over a sealed, verified, constraint-checking pipeline is the end the four-repo stack (agentic-mbse → sysml-codegen → generated package → teax) serves.

Preserved, not strengthened

Honest caveats

These are the limits that are still real at merged main. They are stated exactly as the docs hedge them — not softer, not solved. (Several caveats that were true in earlier generations of this explainer are gone: the ten-offender V11 abort, the "constraints are dropped" era, the separate aggregation resolver, snapshot v1–v3. They are history, and this page does not present them as open.)

  • attribute :>> attr = <expression> is silently dropped at extraction. Use the bare :>> attr = value form. agentic-mbse WARNs on the expression form, but codegen extraction still drops it. Genuinely unsupported (→ the trap).
  • EXPOSE_COMPUTED is rejected — a calc-output reference mixed with arithmetic produces no module and no alias, and the name does not surface. Model the adjustment as a calc def instead.
  • A :>> override on a usage nested inside an instantiated part def loses its literal ([NESTED-OCCURRENCE-OVERRIDE], backlog P2; probe tests/fixtures/nested_occurrence_override_probe/). Capture is definition-relative while demand resolves occurrence-relative, so the supplied-value materializer never matches. It drops on both paths — silently to a manual-required entry point on the calc path, and as a halt under strict resolution on the constraint path. Genuinely unsupported at merged main — surfaced by the lifecycle epic, filed, not fixed. Use the flat and array deep-path shapes, which capture correctly.
  • The constraint catalog is embedded on the graph as the sole schema authority, not emitted standalone. This is the ratified design (owner decision D-3), not a gap: TEAx consumes the embedded catalog directly, a standalone constraint_catalog.json export is explicitly out of scope, and any future export must be mechanically identical to the embedded schema.

SysML v2 glossary

SysML v2
The systems-engineering modeling language. Models here are plain text (.sysml), parsed into an AST by the syside toolchain.
part def / part
part def 'PV Module' is a reusable definition (a blueprint); part pv_module : 'PV Module' [20] is a usage — an instance in a design, here with multiplicity 20.
calc def / calc
calc def EnergyProductionCalc declares an algorithm with typed inputs and outputs; calc energy_production : EnergyProductionCalc { ... } instantiates it and binds its inputs.
binding
in annual_energy_mwh = energy_production.annual_energy_mwh; — wires a calc input to a source: a dotted chain, a qualified name, a sibling attribute, or a literal.
:>> redefinition
The load-bearing idiom: override a value (:>> wattage = 400.0), delegate to a calc output (:>> capital_cost = cost_model.total_cost), reach through the hierarchy (:>> pv_module.wattage = 400.0), or retype (part :>> driver : 'HIF Driver').
EXPOSE pattern
A design attribute that purely forwards a calc output (attribute total_cost : Real = cost_calc.cost;) — surfacing an internal value at the part boundary, with no computation.
sum() aggregation
:>> capital_cost = sum(pv_module.capital_cost) + ... — a roll-up over arrayed children, compiled to count × per-instance value (uniform arrays assumed).
assert constraint
assert constraint affordable : 'Cost Within Budget' { ... } — a modeled assertion; admitted ones lower to CONSTRAINT modules and execute (Kleene three-valued).
EQN / PQN / channel
Identifiers derived once at extraction, __-separated (ADR-003): a module name is the lowercase execution qualified name; an output channel is usage_qn__output_name.
