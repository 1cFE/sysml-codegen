# 08 -- Generation: Rendering the ComputationGraph into Code

The generation layer takes the [ComputationGraph](09-data-models.md#resolution-models)
-- the fully-resolved pipeline specification -- and renders it into executable
Python code, pipeline YAML, and JSON input templates via Jinja2 templates.

Source: `generation/pipeline.py`, `modules.py`, `schemas.py`, `stencils.py`,
`entry_point.py`, `registry.py`, and 12 Jinja2 templates in `templates/`.

## Requirements

| ID | Requirement | Verified by |
|----|-------------|-------------|
| REQ-GEN-01 | [Pipeline YAML generation](21-pipeline-yaml-generation.md) SHALL consume only `ComputationGraph` -- no [extraction models](01-extraction.md). | `generate_pipeline_yaml(graph, package_name, template_env)` signature has no `CalculationDefinitionData` |
| REQ-GEN-02 | Every [PipelineModule](09-data-models.md#resolution-models) SHALL produce exactly one module wrapper file in `modules/`. | One `generate_teax_module()` call per calc def |
| REQ-GEN-03 | Multi-output modules (2+ outputs) SHALL get a `MultiOutput` schema in `schemas/`; single-output modules SHALL use `RootModel[float]` directly. | `should_use_multioutput(calc_def)` gates schema generation |
| REQ-GEN-04 | FULLY_COMPILABLE calc defs SHALL produce auto-implemented stencils; all others SHALL produce `NotImplementedError` stubs. | `generate_implementation()` dispatches on `CalcDefCompilationResult.compilability` |
| REQ-GEN-05 | Each [ParameterGroup](09-data-models.md#resolution-models) SHALL produce one JSON template (`inputs/`) and one Pydantic schema (`schemas/`). | `generate_all_derived_jsons_from_graph()` and `generate_all_derived_schemas_from_graph()` iterate groups |
| REQ-GEN-06 | SysML type mapping (`Real`->`float`, `Integer`->`int`, `Boolean`->`bool`, `String`->`str`) SHALL be consistent across all generators. | Currently VIOLATED: 4 copies of `_map_input_type()` with subtle differences (refactor target) |
| REQ-GEN-07 | Every generated module SHALL be registered in `__init__.py` for TEAx framework discovery. | `generate_registry_function()` produces `MODULE_REGISTRY` dict |

## Output Artifacts

### a. Pipeline YAML (`pipelines/`) -- generated by `pipeline.py`

Defines execution order, module wiring, [entry points](06-entry-point-classifier.md),
and exit points. See [21-pipeline-yaml-generation](21-pipeline-yaml-generation.md)
for channel format rules and type mapping.

```yaml
modules:
  entry_fusion:
    module_type: EntryPoint
    inputs:
      library_params: LibraryParams ../inputs/library_params.json
      design_params: DesignParams ../inputs/design_params.json

  design__plant__energy_production:
    module_type: solarbatterylibrary.EnergyProductionCalcModule
    inputs:
      p_net_mw: float design_params.Design__plant__energy_production__p_net_mw
    outputs:
      root: RootModel[float] Design__plant__energy_production__annual_energy_mwh

  exit_point:
    module_type: ExitPoint
    outputs:
      Design__plant__energy_production__annual_energy_mwh: RootModel[float] ...
```

### b. TEAx Module Wrappers (`modules/`) -- generated by `modules.py`

Python files that validate inputs, call the handwritten implementation,
and return a `ModuleResult`.

```python
class EnergyProductionInput(BaseModel):
    p_net_mw: float = Field(..., description="Net power capacity")

class EnergyProductionCalcModule(ModuleBase[EnergyProductionInput, Float]):
    def run(self, p_net_mw: float) -> ModuleResult[Float]:
        validated = self.validate_and_fill_default(p_net_mw)
        from pkg.handwritten.energy_production_impl import run_energyproductioncalc
        result = run_energyproductioncalc(validated)
        return ModuleResult(data=Float(result))
```

Single-output modules return `Float` (`RootModel[float]`). Multi-output
modules return a named `MultiOutput` Pydantic model.
See [22-output-schema-rules](22-output-schema-rules.md).

### c. Implementation Stencils (`handwritten/`) -- generated by `stencils.py`

Skeleton files for calculation logic. Auto-populated for
[FULLY_COMPILABLE](14-expression-compiler.md) calc defs (REQ-GEN-04):

```python
# Stub (NOT_COMPILABLE):
def run_energyproductioncalc(inputs: EnergyProductionInput) -> float:
    raise NotImplementedError("Manual implementation required.")

# Auto-implemented (FULLY_COMPILABLE):
def run_energyproductioncalc(inputs: EnergyProductionInput) -> float:
    return inputs.p_net_mw * inputs.n_mod * 8760 * inputs.plant_availability
```

Existing manual implementations are preserved by
[smart-regen](23-smart-regen-preservation.md).

### d. Pydantic Schemas (`schemas/`) -- generated by `schemas.py`

Multi-output calculations (2+ outputs) get a `MultiOutput` schema (REQ-GEN-03).

```python
class PVModuleCostOutput(MultiOutput):
    material_cost: float = Field(description="Material cost [USD]")
    fab_cost: float = Field(description="Fabrication cost [USD]")
    total_cost: float = Field(description="Total cost [USD]")
```

Single-output modules use `RootModel[float]` directly -- no schema file.
See [22-output-schema-rules](22-output-schema-rules.md) for Field constraints.

### e. JSON Input Templates (`inputs/`)

Pre-filled JSON files for [entry point parameter groups](06-entry-point-classifier.md),
with defaults from the SysML model.

```json
{
  "Design__plant__energy_production__p_net_mw": 100.0,
  "Design__plant__energy_production__n_mod": 500.0
}
```

### f. Module Registry (`__init__.py`) -- generated by `registry.py`

Registers all modules for TEAx framework discovery (REQ-GEN-07).
See [20-module-registry-generation](20-module-registry-generation.md).

```python
MODULE_REGISTRY = {
    "EnergyProductionCalcModule": EnergyProductionCalcModule,
    "PVModuleCostCalcModule": PVModuleCostCalcModule,
}
```

## The Gold Standard: `pipeline.py` (REQ-GEN-01)

`pipeline.py` ONLY consumes the [ComputationGraph](09-data-models.md#resolution-models):

```python
def generate_pipeline_yaml(
    graph: ComputationGraph,
    package_name: str,
    template_env: Environment,
) -> str:
```

No `CalculationDefinitionData`. No raw extraction artifacts. The implementation
is a series of transformations from graph objects to template dicts:

1. Build `channel_field_map` from [module outputs](09-data-models.md#resolution-models)
   (for `.root` extraction -- see [21-pipeline-yaml-generation](21-pipeline-yaml-generation.md)).
2. Convert [ParameterGroup](09-data-models.md#resolution-models) list to entry point dicts.
3. Convert each [PipelineModule](09-data-models.md#resolution-models) to a
   context dict with typed inputs/outputs.
4. Collect all output channels as exit points.
5. Render `pipeline_yaml.jinja2`.

This is the target architecture for all generators.

## Current Gap (REQ-GEN-06, REQ-PIPE-07 — see [26](26-pipeline-module-migration.md))

The other generators consume raw [CalculationDefinitionData](09-data-models.md#extraction-models):

```python
def generate_teax_module(calc_def: CalculationDefinitionData, ...)     # modules.py
def generate_multioutput_model(calc_def: CalculationDefinitionData, ...) # schemas.py
def generate_implementation(calc_def: CalculationDefinitionData, ...)   # stencils.py
```

They re-derive information the graph already contains. Each has its own
`_map_input_type()` doing the same `"Real" -> "float"` mapping -- **4 copies**
across `modules.py`, `schemas.py`, `stencils.py`, and `entry_point.py` with
subtle differences (some default unknown types to `"float"`, others pass through).

Problems:
- **Duplicated logic** -- type mapping, [naming](15-naming-conventions.md),
  output pattern detection repeated across files.
- **Drift risk** -- [graph builder](05-module-factory.md) changes may not propagate.
- **Missing graph context** -- wrappers do not see wiring information; they only
  see the calc def's abstract parameter list.

Ideal end state: all generators accept `PipelineModule` or the full
`ComputationGraph` as primary input (like `pipeline.py`). Raw extraction
data only for documentation metadata (doc comments, source locations).

## Template System

| Template | Generator | Output |
|---|---|---|
| `pipeline_yaml.jinja2` | `pipeline.py` | Pipeline YAML |
| `teax_module.py.jinja2` | `modules.py` | Module wrappers |
| `teax_module_stub.py.jinja2` | `modules.py` | Module stub wrappers |
| `implementation_stencil.py.jinja2` | `stencils.py` | Stub stencils |
| `auto_implementation.py.jinja2` | `stencils.py` | Auto-impl stencils |
| `multioutput_model.py.jinja2` | `schemas.py` | Multi-output schemas |
| `pydantic_schema.py.jinja2` | `schemas.py` | Pydantic schemas |
| `entry_point_schema.py.jinja2` | `entry_point.py` | Entry point schemas |
| `parameter_group_schema.py.jinja2` | `entry_point.py` | Parameter group schemas |
| `constraint_validator.py.jinja2` | `schemas.py` | Constraint validators |
| `registry_function.py.jinja2` | `registry.py` | Module registry |
| `test_implementations.py.jinja2` | `stencils.py` | Test scaffolding |

The rendering flow (pipeline YAML as example):

```
ComputationGraph
  --> pipeline.py builds context dict {entry_points, modules, exit_points}
    --> pipeline_yaml.jinja2 renders with {% for module in modules %}
      --> YAML string written to pipelines/pipeline.yaml
```

Every generator follows this pattern: build context dict, render template,
write to disk.

### Template context variables (key generators)

**`teax_module.py.jinja2`** (via `modules.py`):
`module_name`, `class_name`, `input_class_name`, `input_attributes[]` (name,
type_hint, description, default), `output_attributes[]`, `output_type_name`,
`num_outputs`, `is_multi_output`, `implementation_function_name`, `package_name`.

**`implementation.py.jinja2`** (via `stencils.py`):
`function_name`, `input_fields[]` (name, type), `output_fields[]` (name, type),
`return_type`, `compiled_expression | None`, `calc_expressions[]`.

**`entry_point_schema.py.jinja2`** (via `entry_point.py`):
`class_name`, `fields[]` (name, type, default_value, description), `package_name`.
