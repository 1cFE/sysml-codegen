## Overview

Design the E2E validation test suite for computed attribute pipeline modules. Tests run the full codegen pipeline (`run_codegen`) on the existing probe fixture and solar_battery model, then execute generated auto-implementations and assert numerical correctness against hand-computed ground truth values.

## Research Findings

### Existing E2E Test Pattern (`test_expression_compilation_e2e.py`)

The established pattern for E2E validation uses:

1. **Class-scoped fixture** that runs `run_codegen()` once and returns the output path (`tests/integration/test_expression_compilation_e2e.py:132-143`)
2. **`find_impl_files(output_path)`** to discover all generated `_impl.py` files (`tests/helpers/impl_execution.py:15-25`)
3. **`is_auto_implemented(path)`** to check for `AUTO_IMPLEMENTED = True` marker (`tests/helpers/impl_execution.py:28-31`)
4. **`extract_function_body(path)`** to get executable function body from impl file (`tests/helpers/impl_execution.py:34-88`)
5. **`execute_impl_body(body, inputs, outputs)`** to run the body with a `SimpleNamespace` and collect results (`tests/helpers/impl_execution.py:91-122`)
6. **`assert_outputs_match(actual, expected, tolerance)`** to compare with relative tolerance (`tests/helpers/impl_execution.py:125-151`)

This is the exact pattern we'll follow for computed attribute E2E tests. No new helpers needed.

### Auto-Implementation Template Structure

Generated `_impl.py` files for computed attributes follow the `auto_implementation.py.jinja2` template (`src/sysml_codegen/templates/auto_implementation.py.jinja2`):

```python
AUTO_IMPLEMENTED = True
from {package}.modules.{path} import {InputClass}

def run_{module_name}(inputs: {InputClass}) -> float:
    """docstring"""
    return {compiled_expression}
```

For a single-output FORMULA like `area = length * width`, the generated body is:
```python
return (inputs.length * inputs.width)
```

The `extract_function_body` + `execute_impl_body` helpers handle this pattern: they extract the body after the `def` line and docstring, wrap it in a fresh function, call it with `SimpleNamespace(**input_dict)`, and return the result.

### Impl File Discovery for Computed Attributes

`find_impl_files()` searches `output_path / "handwritten"` recursively for `*_impl.py`. Computed attribute impls are generated by `_generate_computed_attr_stencils()` (`src/sysml_codegen/cli/__init__.py:313-395`) into the same `handwritten/` directory tree using ADR-003 namespacing. The helper `_find_impl(output_path, calc_name)` does case-insensitive substring matching on the filename.

For the probe fixture (package `AttrExprProbeDesign`, part `probe_design`), a computed attribute `area` would generate impl at:
`handwritten/attrexprprobedesign/probe_design/area_impl.py`

And `_find_impl(output, "area")` would find it since `"area" in "area_impl.py"` is true. However, this could match ambiguously if multiple impl files contain "area" (e.g., `area_impl.py` and `scaled_area_impl.py` both match `"area"`). We need a more precise lookup for computed attributes.

### Solar Battery `p_net_kw`

From `tests/fixtures/solar_battery_model/design.sysml:60`:
```sysml
attribute p_net_kw : Real = p_net_mw * 1000.0;
```

This is a FORMULA computed attribute with `p_net_mw = 0.008` as the literal sibling. The compiled expression should be `(inputs.p_net_mw * 1000.0)`, producing `8.0`.

Downstream: `annualized_om` CalcUsage (`design.sysml:74-77`) binds `in p_net_kw = p_net_kw`, which after Item 3 should resolve as MODULE_OUTPUT from the `p_net_kw` synthetic module rather than as an ENTRY_POINT.

### Existing Test Count

The existing Phase 1 E2E test (`test_expression_compilation_e2e.py:145-148`) already expects 16 impl files for solar_battery (15 CalcDefs + 1 computed attr `p_net_kw`). This was updated as part of Item 3.

## Proposed Design

### Architecture

One new test file: `tests/integration/test_computed_attributes_e2e.py`

Three test classes mirroring the established pattern in `test_expression_compilation_e2e.py`:
1. `TestProbeComputedAttrsE2E` -- Probe fixture validation
2. `TestSolarBatteryComputedAttrE2E` -- Solar_battery validation
3. `TestPhase1Regression` -- Explicit regression check (lightweight, confirms existing E2E tests' models still work)

### Component 1: Probe Fixture E2E (`TestProbeComputedAttrsE2E`)

**Purpose:** Run the full codegen pipeline on `tests/fixtures/attr_expr_probe/`, then execute each FORMULA computed attribute's auto-implementation and verify numerical correctness.

**Class-scoped fixture:** `probe_output`
- Calls `run_codegen(GenerationConfig(models_path=probe_path, output_path=..., package_name="attr_expr_probe"))`
- Returns the output path
- Pattern: identical to `TestSolarBatteryValidation.solar_battery_output` (`test_expression_compilation_e2e.py:132-143`)

**Test 1: `test_codegen_succeeds`**
- Assert `run_codegen` returns True
- Assert `handwritten/` directory exists

**Test 2: `test_formula_modules_auto_implemented`**
- Find all impl files via `find_impl_files()`
- Filter to those that are `is_auto_implemented()`
- Assert count >= 9 (the 9 FORMULA attributes from the ground truth table, plus additional FORMULAs like `total_dim`, `net_length`, `gross_electric_simple`, `p_neutron`, `p_blanket_thermal`)
- Also assert the 2 CalcDef impls (ScaleCalc, SplitCalc) are auto-implemented

**Test 3: `test_ground_truth` (parametrized)**
- Parametrized over the 9 ground-truth entries from the spec
- For each: find the impl file, extract body, execute with input dict, compare with `assert_outputs_match`
- Use `pytest.approx` / `assert_outputs_match` with default tolerance (1e-10) for exact values, which is sufficient since these are simple float arithmetic

**Ground truth data structure:**
```python
PROBE_GROUND_TRUTH = [
    # (attr_name_substring, input_dict, output_name, expected_value)
    ("area", {"length": 10.0, "width": 5.0}, "area", 50.0),
    ("volume", {"length": 10.0, "width": 5.0, "height": 3.0}, "volume", 150.0),
    ("cost", {"area": 50.0, "rate": 12.0}, "cost", 600.0),
    ...
]
```

**Impl file lookup:** Since `_find_impl` does substring matching and names like `"area"` would match `"area_impl.py"` AND `"scaled_area_impl.py"`, we need a more precise lookup. We'll write a local helper `_find_computed_attr_impl(output_path, attr_name)` that matches on the exact filename pattern `{attr_name}_impl.py` (not substring). This avoids false matches while staying consistent with the generated file naming convention.

**Test 4: `test_chain_execution_order`**
- Verify that in the computation graph, chain modules are ordered correctly
- Build a `PipelineContext` or inspect the pipeline YAML to confirm: area before cost, cost before marked_up_cost, both cost and volume before cost_density
- Alternative: simply verify the ground-truth values are correct (Tests 3 already covers this since chain correctness is proven by correct intermediate values fed as inputs)

**Test 5: `test_expose_pure_no_module`**
- After codegen, verify no impl file exists for EXPOSE_PURE attributes (`scale_result`, `half_vol`, `quarter_vol`)
- These should not have `_impl.py` files generated

**Test 6: `test_expose_computed_no_module_no_error`**
- Verify no impl file exists for `scaled_area` (EXPOSE_COMPUTED)
- Verify codegen did not fail (already covered by fixture succeeding)

**Test 7: `test_backlog_accuracy`**
- Read `IMPLEMENTATION_BACKLOG.md` from output
- Assert "0 functions to implement" present (all CalcDefs + all computed attrs are auto-implemented in the probe fixture)

### Component 2: Solar Battery Computed Attr E2E (`TestSolarBatteryComputedAttrE2E`)

**Purpose:** Validate that `p_net_kw` computed attribute generates correctly in the real solar_battery model and wires to downstream calcs.

**Class-scoped fixture:** `solar_battery_output`
- Identical to `TestSolarBatteryValidation.solar_battery_output` pattern
- Calls `run_codegen()` on `tests/fixtures/solar_battery_model/`

**Test 1: `test_p_net_kw_module_generated`**
- Find impl file for `p_net_kw` computed attribute
- Assert `is_auto_implemented()` is True

**Test 2: `test_p_net_kw_ground_truth`**
- Execute the `p_net_kw` impl with `{"p_net_mw": 0.008}` (the literal from `design.sysml:53`)
- Assert result == `8.0` (0.008 * 1000.0)

**Test 3: `test_p_net_kw_wiring_in_pipeline_yaml`**
- Read the generated pipeline YAML
- Verify the `annualized_om` module's `p_net_kw` input is sourced from the computed attribute module's output channel (not listed as an entry point)
- This validates FR-6 (MODULE_OUTPUT, not ENTRY_POINT)

**Test 4: `test_impl_count_includes_computed_attr`**
- Assert total impl file count == 16 (15 CalcDefs + 1 computed attr)
- This overlaps with the existing test in `test_expression_compilation_e2e.py:145-148` but explicitly verifies in the Item 4 context

**Test 5: `test_existing_ground_truth_unchanged`**
- Re-run the same 5 ground-truth parametrized test cases from `SOLAR_BATTERY_GROUND_TRUTH` in `test_expression_compilation_e2e.py`
- This is the regression proof: computed attribute addition didn't break CalcDef auto-implementations
- To avoid duplication, we can reference the same test data constant or simply assert the same 5 cases. Since we're running a fresh codegen in our fixture, this is a genuine independent re-validation.
- However, since `test_expression_compilation_e2e.py` already runs these tests and Item 3 didn't change CalcDef generation, we should keep this lightweight. Instead of re-parametrizing all 5, we test one representative case (e.g., `annualizedomcalc` since it directly consumes `p_net_kw`).

**Test 6: `test_annualized_om_uses_computed_p_net_kw`**
- Execute the `annualizedomcalc` auto-impl with `{"om_rate_per_kw_year": 20.0, "p_net_kw": 8.0}`
- Assert result `annual_om_cost` == `160.0` (20.0 * 8.0)
- The `p_net_kw` value `8.0` is the output of the computed attribute module, proving the end-to-end chain: literal `p_net_mw=0.008` -> computed `p_net_kw=8.0` -> CalcUsage `annualized_om` input

### Component 3: Phase 1 Regression Guard (`TestPhase1Regression`)

**Purpose:** Explicitly confirm that Phase 1 E2E test models still pass after Item 3 changes.

This is lightweight -- the real regression proof is that the existing `test_expression_compilation_e2e.py` tests continue to pass in CI. But we add a minimal guard:

**Test 1: `test_chain_spike_still_works`**
- Run codegen on `chain_spike_model/`
- Assert success + 3 impl files + all auto-implemented
- This is a fast sanity check (chain_spike is the simplest model)

**Test 2: `test_catf_mfe_still_works`**
- Run codegen on `catf_mfe_model/`
- Assert success + 21 impl files (not more, not fewer -- computed attrs shouldn't be extracted from the CATF model since it doesn't use attribute expressions)
- This confirms zero false-positive computed attribute extraction on a model that only uses CalcDefs

### Impl Lookup Helper

A local helper to avoid substring ambiguity:

```python
def _find_computed_attr_impl(output_path: Path, attr_name: str) -> Path:
    """Find the impl file for a computed attribute by exact name match."""
    target = f"{attr_name}_impl.py"
    for impl in find_impl_files(output_path):
        if impl.name == target:
            return impl
    raise FileNotFoundError(
        f"No impl file named '{target}' in {output_path / 'handwritten'}"
    )
```

This is narrower than `_find_impl()` from `test_expression_compilation_e2e.py:56-63` which does substring matching. For computed attributes, exact-name matching prevents `"area"` from finding `"scaled_area_impl.py"`.

### Pipeline YAML Inspection

For Test 3 of `TestSolarBatteryComputedAttrE2E`, we need to verify wiring in the pipeline YAML. The approach:

1. Read `output_path / "pipelines" / "pipeline.yaml"`
2. Parse as YAML
3. Find the `annualized_om` module entry
4. Check that its `p_net_kw` input references the computed attribute module's output channel
5. Alternatively: check that `p_net_kw` does NOT appear in the entry points section of the YAML

This is a structural assertion, not a numerical one, but it directly validates FR-6.

## Potential Risks

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| Probe fixture codegen fails due to EXPOSE_COMPUTED patterns | Low | `run_codegen` should handle EXPOSE_COMPUTED gracefully (skip, don't error). If it fails, that's a bug to fix before tests pass. |
| Impl file naming doesn't match expected pattern | Low | The naming follows ADR-003, which is well-tested in unit tests. Exact-name lookup helper handles ambiguity. |
| Solar battery `p_net_kw` not extracted as computed attribute | Low | Item 3 integrated Step 4.5. If not extracted, test failure surfaces the bug. |
| CATF model has unexpected computed attributes | Low | CATF uses CalcDefs exclusively. If computed attrs are falsely detected, the impl count assertion catches it. |
| Floating-point tolerance too tight | Low | Default 1e-10 relative tolerance is generous for simple float arithmetic. The only non-trivial case is `p_alpha` (division), which is well within 1e-10. |

## Integration Strategy

- New file `tests/integration/test_computed_attributes_e2e.py` -- no modification to existing files
- Uses the same `tests/helpers/impl_execution.py` utilities as existing E2E tests
- Uses the same conftest fixtures (`fixtures_path`, model path fixtures)
- Existing `test_expression_compilation_e2e.py` continues to run unchanged as an independent regression guard
- The validation report (`.project/active/attr-expr-e2e/report.md`) is a manual post-execution artifact, not auto-generated by the tests

## Validation Approach

1. **Run the new test file:** `uv run pytest tests/integration/test_computed_attributes_e2e.py -v`
2. **Run full test suite:** `uv run pytest tests/` to confirm zero regressions
3. **Manual review:** Inspect generated output for probe fixture to verify FORMULA impls look correct
4. **Write report:** After all tests pass, write `.project/active/attr-expr-e2e/report.md` with per-pattern results
