## Problem

The canonical constraint inventory can now retain every constraint usage, but an asserted
constraint owned by a calculation definition still cannot attach to any calculation occurrence.
Such a usage receives `non_reaching / owner_kind_unattachable / error` even when the graph contains
concrete calculations of its owning definition. Leaving that behavior in place would make the
agent-originated Q2 rule ratified by the owner—one asserted check per concrete calculation
occurrence—visible but permanently unexecutable.

The gap is not a missing definition lookup. **[AGENT — executable evidence, 2026-08-13]** The Item 6
probe matched the constraint owner's exact `DeclarationId` to
`CalcNode.calculation_definition_id`, selected zero, one, and two calculation occurrences, and
recovered explicit actuals and a modeled default without rendered-name lookup
(`probes/findings.md`). It also found two boundaries the implementation contract must respect:

- two sibling uses of one calculation definition can share a part scope, so scope plus constraint
  usage identity collapses two required checks into one; concrete check identity must include the
  full `CalcNode.node_id`;
- the exact owner/formal facts needed for attachment exist together inside elaboration but are not
  both serialized today, so attachment and formal resolution must finish there before snapshot
  encoding.

This item specifies the follow-on capability and its public proof. It does not implement production
behavior in this epic. The capability must extend the canonical usage and occurrence authority that
already exists. A second inventory, post-build fill, or reconstruction from rendered names would
recreate the authority split the elaborate-first architecture removed.

## Success Criteria

The acceptance cases below are public-path outcomes. Unit and mutation tests may supplement them,
but internal graph construction alone does not satisfy a live or snapshot criterion.

- [ ] **Zero occurrences are visible and correctly caused.** A model with one admitted asserted
      calc-definition-owned usage and no concrete calculation occurrence generates on the live,
      in-place-snapshot, and relocated-snapshot routes. All three carry one usage record with
      `non_reaching / owner_has_no_occurrences / warning`, zero concrete entries, and a
      partial-coverage report unless the usage is explicitly inapplicable.
- [ ] **One occurrence produces one check.** A model with one concrete calculation occurrence
      generates exactly one concrete constraint entry, module, aggregator input, and result joined
      to one usage-tier record. Live, in-place-snapshot, and relocated-snapshot generation agree on
      identities, catalog values, report values, and generated bytes.
- [ ] **Many occurrences produce many distinct checks.** Repeated uses of the same calculation
      definition, including two sibling uses under one part scope, produce exactly one concrete
      check per `CalcNode`. One usage-tier carrier reports the exact occurrence count; concrete
      check and result identities remain distinct and stable on all three routes.
- [ ] **Every formal source is shared with its calculation occurrence.** Public generation proves
      explicit design-attribute and literal actuals, a modeled default, and a defaultless/unbound
      formal. Each calculation and its gate consume the same semantic source and projected entry
      point or producer channel; no gate-only duplicate entry point is minted.
- [ ] **Polarity is correct per occurrence.** Positive `assert constraint` and
      `assert not constraint` uses preserve one polarity-neutral predicate and apply their own
      polarity exactly once to every occurrence. Boundary, true, false, and indeterminate cases
      produce complementary positive/negated status and margin behavior where the existing profile
      defines a margin.
- [ ] **One failed occurrence cannot be hidden.** In a repeated-definition model with distinct
      occurrence values, a failure in one occurrence yields a `violation` headline, preserves the
      passing siblings' results, and identifies the failing calculation occurrence exactly. No
      definition-level or usage-level roll-up can convert the population to satisfaction.
- [ ] **Usage coverage and occurrence results remain distinct.** For one applicable asserted usage
      expanded to `N` concrete calculations, the report shows one assessed usage and `N` assessed
      entries/results. Full satisfaction is possible only when every expected occurrence result is
      present and satisfied; a missing or extra result is a named execution/report failure.
- [ ] **Report volume is complete and deterministic.** A many-occurrence public fixture emits one
      ordered result per concrete check with no sampling, truncation, or same-definition collapse.
      Regeneration and snapshot replay preserve the ordering and exact drill-down identities.
- [ ] **Unsupported cases fail closed before output mutation.** Profile `BLOCK`, a missing or
      ambiguous exact owner/formal association, a duplicate concrete identity, a partial
      occurrence expansion, and a broken catalog join each produce a named diagnostic and no
      generated target tree. None is recast as `owner_has_no_occurrences`, a plain exclusion, or a
      best-effort partial population.
- [ ] **Schema and sealing transitions are explicit.** The new calculation-occurrence identity
      round-trips through the versioned instance-graph snapshot, projection receipt, embedded
      catalog, model contract, and package seal. Old, unknown, or malformed shapes fail closed;
      compatible consumer pins land in a recorded producer-first order.
- [ ] **The capability remains one authority.** Static boundary checks and public mutation tests
      show no second constraint/occurrence inventory, rendered-name attachment, post-build fill, or
      projection-time semantic reconstruction.

## Known Requirements

### Eligibility and asserted polarity

- **[INHERITED: `rulings-20260812.md` Q2]** An asserted constraint owned by a calculation
  definition means one executable check per concrete calculation occurrence. The usage is one
  authored feasibility gate even when it expands to many concrete checks.
- **[INHERITED: `constraint-semantics-contract/spec.md` Q1 and Q7]** Only asserted source forms are
  candidates for execution. A plain calc-definition-owned `constraint` stays visible and
  non-executable; requirement-side forms stay visible and out of executable scope.
- **[INHERITED: lifecycle contract invariants 8–12]** An asserted occurrence becomes executable
  only when the profile returns `ADMIT` and contextual attachment, binding, graph, and compilation
  validation all succeed. `BLOCK` still halts the model; `NON_NUMERICAL` or `UNASSESSED` remains a
  visible unassessed disposition.
- **[INHERITED: lifecycle contract invariants 5, 6, 29]** The effective predicate remains a
  polarity-neutral semantic body. Each source-authored usage carries its own `is_negated`, and
  each concrete occurrence derives `expected_value = not is_negated`; polarity is applied once to
  truth, status, and simple margin, never folded into or compiled into a second predicate body.
- **[INHERITED: lifecycle contract Appendix C, “Positive/negated × inline/definition-typed”]**
  `assert not constraint` expects the positive predicate to be false. Negating an indeterminate
  predicate remains indeterminate; it is never converted to satisfaction.
- **[INFERRED]** Eligibility is all-or-nothing for an authored usage's finite occurrence set. If
  any required occurrence cannot be attached or bound exactly, generation fails rather than
  emitting checks for only the occurrences that happened to succeed.

### Exact attachment and occurrence identity

- **[AGENT — executable evidence: `probes/findings.md`]** Attachment selects `CalcNode`s only by
  equality between the constraint owner's `DeclarationId` and
  `CalcNode.calculation_definition_id`. A qualified definition name, calculation display path,
  part scope, iteration order, or rendered module name is never an attachment key.
- **[AGENT — executable evidence: `probes/findings.md`]** Zero, one, and many matches are lawful
  results of that exact selection. Repeated uses of one definition remain separate because their
  full `CalcNode.node_id` values are separate even when their part scope is the same.
- **[AGENT — executable evidence: `probes/findings.md`]** Stable concrete check identity contains
  both the authored constraint usage `DeclarationId` and the full matched `CalcNode.node_id`.
  Scope plus constraint declaration is insufficient. The graph-native type that carries this
  information is deferred to design; the information content is not.
- **[INHERITED: lifecycle contract invariants 17, 27, 28]** Every finite occurrence gets a distinct
  execution ID, catalog entry, module, result channel, and result. Identity includes source-local
  identity, concrete occurrence, membership, and polarity; a shared predicate or producer does not
  collapse concrete execution identity.
- **[INFERRED: Q2/Q5 identity consequence]** One canonical join must work in both directions: the usage-tier
  `declaration_id` joins to every concrete entry, and each concrete entry exposes the exact
  calculation occurrence that caused it. A consumer can move from a usage-level coverage row to
  all results and from a result back to its one usage and one calculation occurrence without
  parsing names.
- **[INHERITED: lifecycle contract invariant 18]** Recursive, non-finite, malformed, or partially
  expanded occurrence sets fail loudly. No partial set is cataloged or reported.

### Formal binding and source reuse

- **[AGENT — executable evidence: `probes/findings.md`]** Formal attachment happens while the
  canonical feature-slot index and the matched `CalcNode` are both in scope. For each required
  calculation-definition formal, exact root identity must select one and only one input on that
  calculation occurrence.
- **[INHERITED: lifecycle contract invariants 19, 20, 26]** Calculation inputs and constraint
  actuals use the same positive-resolution authority. A real producer channel wins, then a real
  design attribute; no display-text parse, name coincidence, fallback guess, late fill, or
  consumer-local reconstruction is supported.
- **[INFERRED: probe evidence and lifecycle invariants 19/20/26]** An explicit actual reuses the matched calculation occurrence's resolved `InputRef`.
  This includes a producer channel, design-attribute node, and authored usage literal. The gate
  does not resolve the authored expression a second time.
- **[INHERITED: lifecycle contract invariants 19 and 22]** An omitted formal may use a modeled
  default only when the calculation definition declares one. That default remains one independently
  overridable `LIBRARY_DEFAULT` source per concrete calculation occurrence unless the model
  explicitly shares a source.
- **[INFERRED: lifecycle invariant 22 source-reuse consequence]** A modeled default used by both the calculation and its gate projects as one entry
  point for that calculation occurrence/formal. The gate reuses it; it does not mint a separate
  constraint-scoped default.
- **[HARD: existing exact projection interface]** A defaultless unbound calculation formal projects
  as a valueless `LIBRARY_DEFAULT` entry point that the package user must supply. The gate must
  consume that same occurrence/formal entry point. It may not turn absence into a new default or
  mint a second required public field.
- **[INFERRED]** Definition-typed constraint actuals continue through the existing constraint
  formal-resolution path, but any reference to a calculation formal first resolves to the matched
  calculation occurrence's already-decided source. This adds no calc-definition-specific entry
  point or resolver lane.
- **[INFERRED: probe exact-match integrity consequence]** A missing, duplicate, or contradictory exact formal match is a named, usage- and
  occurrence-identifying generation error. It is not an unbound-formal fallback unless the model
  actually left that formal unbound.

### Cause-based diagnostics and disposition transition

- **[INHERITED: `rulings-20260812.md` Q3]** Severity follows the cause. Structurally
  unattachable asserted usages halt; asserted usages on an attachable owner with zero concrete
  occurrences are warning-grade and visible; plain and out-of-scope forms remain visible without a
  form-caused error.
- **[INHERITED: `rulings-20260812.md` Q5 and post-ruling refinement L2-2]** A vacuous asserted
  usage remains an applicable but unassessed gate and holds coverage at partial until the model
  creates an occurrence or records explicit inapplicability.
- **[INFERRED: Q2/Q3 capability consequence]** Once this capability is present, `calc_def` is an attachable owner kind. For an
  admitted asserted usage, a nonempty exact match set transitions from
  `owner_kind_unattachable` to `eligible`; an empty exact match set transitions to
  `owner_has_no_occurrences`. A supported calc-definition owner never remains
  `owner_kind_unattachable` merely because it owns the constraint.
- **[INFERRED]** Failure to establish the owner definition identity or the integrity of the match
  is not a zero-occurrence result. Missing/duplicate owner identity, malformed node identity, and
  missing/duplicate formal association fail by a named structural cause; they never downgrade to
  `owner_has_no_occurrences`.
- **[INHERITED: Item 2 disposition precedence]** For a genuine zero-occurrence set, expansion cause
  wins before profile eligibility. The usage emits no concrete check. Asserted form gives
  `owner_has_no_occurrences / warning`; non-asserted form gives the same visible cause at `info` and
  never enters the feasibility denominator.
- **[INHERITED: Item 2 inapplicability contract and Item 3 D9]** Explicit inapplicability stays
  beside the disposition and can remove only an unassessed gate from the denominator. An eligible
  usage marked inapplicable is an authoring contradiction and fails before output mutation.

### Canonical graph, catalog, projection, and versions

- **[INHERITED: Item 2 D1/D3/D9]** `InstanceGraph.constraint_usages`, keyed by usage
  `DeclarationId`, remains the complete authored domain and the sole usage-tier inventory. Calc-def
  expansion extends the existing per-occurrence `ConstraintNode` authority; it does not add a
  calc-def manifest or another usage list.
- **[AGENT — executable evidence: `probes/findings.md`]** Expansion, binding, and identity creation
  happen inside elaboration before serialization. The serialized usage record lacks the exact
  owner-definition identity, and serialized explicit ports lack the root-formal identity needed to
  reconstruct the match lawfully after build.
- **[INHERITED: elaborate-first architecture and lifecycle contract invariants 20, 26, 35]**
  Projection is one-way over a validated graph. It renders identifiers, modules, entry points,
  catalog rows, and order; it does not rediscover attachment, rerun formal resolution, or repair
  missing semantic data.
- **[INFERRED: Q2/Q5 two-tier join consequence]** `ConstraintUsageRecord.occurrence_count` equals the number of calc-occurrence-backed
  concrete nodes for that declaration. Every node and catalog concrete entry joins to exactly one
  usage record, and every usage count is checked against both graph and catalog populations.
- **[INFERRED: probe identity and Q5 drill-down consequence]** Every concrete catalog entry carries or losslessly joins to the full calculation node
  identity used at attachment. Rendered `owner_instance_path`, `constraint_id`, module names, and
  report labels are display/projection values, never the reverse lookup key.
- **[HARD: current instance-graph codec]** Adding the required calculation-occurrence identity to
  the graph wire shape changes the exact-match instance-graph schema. The implementation must bump
  the embedded instance-graph schema version and refuse the prior or field-incomplete shape; an
  optional field under the old version would permit the identity collapse to reload.
- **[INFERRED: snapshot-versioning consequence]** The implementation design must state whether the surrounding snapshot-envelope
  version also changes. Whichever version rule it chooses, live capture, in-place replay, and
  relocated replay must decode the same concrete identity, and old/unknown combinations must fail
  before projection with recapture guidance.
- **[HARD: current catalog schema]** The existing concrete catalog row does not carry the exact
  calculation node identity and therefore cannot support the required reverse join without name
  reconstruction. The catalog wire contract must add lossless calculation-occurrence identity,
  bump its schema version in the same landing, and require consumers to re-vendor the compatible
  version producer-first.
- **[INHERITED: Item 3 report contract]** This capability changes report population, not the Item 3
  report schema or headline vocabulary. A report-schema change is not authorized here. Any
  unforeseen need to change it is a surfaced scope conflict, not a quiet addition.
- **[INHERITED: contracts/sealing architecture]** Snapshot graph fingerprints, projection receipts,
  embedded catalog fingerprints, the model contract's semantic fingerprint, and the package seal
  cover the new identity and generated occurrence checks. Removing, duplicating, or misjoining an
  occurrence after sealing fails verification or preflight before semantic use.

### Usage-level feasibility and occurrence-level results

- **[INHERITED: `rulings-20260812.md` Q5]** Coverage counts authored usages; results list concrete
  occurrences. One calc-definition usage expanded over `N` calculations contributes one authored
  usage, one applicable/assessed gate when eligible, and `N` assessed entries/results.
- **[INHERITED: Item 3 D2/D3/D6]** `authored_usage_total`, `applicable_gate_total`, and
  `assessed_gate_count` stay usage-tier. `assessed_entry_count` and `results` stay occurrence-tier.
  The catalog fingerprint remains the join to per-usage and per-occurrence detail.
- **[INFERRED: Q5 and Item 3 exact-input consequence]** An eligible usage is coverage-complete only when its expected concrete-entry count
  equals its attached occurrence count and every aggregator input/result is present. A missing or
  extra occurrence result is a schema/execution failure, not partial coverage and not an implicit
  pass.
- **[INHERITED: Item 3 headline precedence]** Any violated occurrence makes the headline
  `violation`; otherwise any indeterminate occurrence makes it `indeterminate`; full satisfaction
  requires all expected occurrences of every applicable usage to be present and satisfied.
- **[INFERRED: Q5 aggregation consequence]** Usage-level or definition-level summaries are derived views only. They preserve the
  worst occurrence state and retain a stable drill-down to every member. They may not replace the
  concrete result list, discard passing siblings, or hide the identity of a failing occurrence.
- **[INFERRED: Q2 per-occurrence consequence]** Report and generated-module volume grows linearly with the number of concrete
  calculation occurrences: one wrapper/module, aggregator input, catalog concrete entry, and
  result per occurrence. Ordering is deterministic by exact graph identity. No sampling,
  truncation, same-definition deduplication, or “first failure only” output is allowed.
- **[INHERITED: lifecycle contract invariant 29]** Reusing one compiled polarity-neutral predicate
  body for a true shared source is allowed and expected. Compilation reuse never reduces the number
  of occurrence wrappers, entries, channels, or results.

## Non-Goals

- Implementing the calc-definition gate capability in production during this epic.
- Converting or executing the 51 CATF calculation-definition guards; Item 5 may continue to mark
  them `awaits-capability` under its owner-approved table.
- Changing the report schema or headline vocabulary already owned and landed by Item 3.
- Evaluating requirement-side `satisfy`, `require`, or `assume` forms.
- Admitting feature chains inside predicate bodies.

## Open Questions / Deferred to design

- **Graph-native identity shape.** The information content is fixed: usage `DeclarationId` plus the
  full `CalcNode.node_id`. Design chooses whether to extend `NodeId`, add a typed occurrence-owner
  field, or introduce another graph-native composite. It may not add a parallel inventory.
- **Construction ordering.** Calculation inputs are resolved after today's constraint population
  point. Design must sequence calc-def expansion so one canonical binding pass feeds calculations
  and gates without a post-build repair pass.
- **Diagnostic and version spellings.** The required failure distinctions and version transitions
  are fixed above; exact diagnostic codes, schema tokens, and coordinated pin commits belong to
  design.
- **Optional summary surface.** A usage- or definition-grouped report view may be designed for
  navigation, but the occurrence-complete report and worst-state aggregation requirements above
  are fixed. The optional view cannot force an Item 3 report-schema change inside this capability.
- **Surfaced premise conflict — do not resolve silently.** The inherited coverage text says a
  profile-`BLOCK`ed asserted usage remains in the feasibility denominator as unassessed, while the
  existing `[HARD]` model rule halts any asserted `BLOCK` that reaches an occurrence before a
  package/report exists. Calc-def attachment makes that reachable case more common. This spec does
  not invent a partial-coverage report for an unbuildable package: acceptance pins the existing
  halt, and the broader denominator wording remains parked for the owner/documentation stage.
