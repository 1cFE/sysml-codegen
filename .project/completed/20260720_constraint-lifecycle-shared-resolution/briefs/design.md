# Design Brief — Lifecycle Item 2: Shared Producer Resolution and Gate A

**Stage:** design (independent design_review follows in a fresh session)
**Spec:** `.project/active/constraint-lifecycle-shared-resolution/spec.md` (just authored;
provenance-graded; five flagged agent bets)
**Same authority chain and scope firewall as the spec brief**
(`briefs/spec.md` in this directory).

## Design mandate

One typed resolution request/result, one ordered positive ladder (real producer channel →
real design attribute under exact QN), strict/lenient divergence only at terminal miss. Serve
all three consumers (calculation, aggregation, constraint) from the one mechanism; delete the
three ladders and the string surgery the spec names at file:line.

## Constraints

1. Build ON Item 1's landed seams (`prepare_constraint_usages`, `resolve_logical_demand`,
   `select_group_source`, `enrich_graph_design_attributes` at certified `287afc4`) — extend or
   consume them; do not rework them. Respect Item 1's recorded contract deviations as facts.
2. The spec's five agent bets are challengeable — the design must either confirm each with code
   evidence or challenge it explicitly (especially: only-two-rungs, aggregation joins the shared
   request, entry-point backfill = post-build mutation under D-1).
3. Gate A: the real shape only — usage-owned attribute on concrete `PartUsage`, self-named
   actual, real evaluated verdict (SR-R21/R22). The def-owned `constraint_inline` fixture is a
   forbidden substitution.
4. No public late fill, placeholder completion, or post-build graph/default mutation. No
   general typed-path/part-index refactor beyond what unification requires.
5. Simplicity is qualitative and binding: deletion over shims; no compatibility alias or route
   adapter; don't collapse intentional strict/lenient semantics into flags threaded everywhere.
6. Fold the implementation plan INTO the design (owner pace directive): phase the work
   (test-first, RED-before-GREEN on public fixtures per Item 1's discipline), name per-phase
   validation commands, and define stop conditions. A separate plan.md will not be produced.

## Design shape

Data contracts (exact records/APIs with fields), resolution semantics (rung order, terminal
behavior, error taxonomy with context requirements), consumer integration (how each of the
three call sites converges), deletion inventory, phased execution with commands, and risks
with named counterexamples. Keep Item 1's design as the rigor template; where the spec settles
a question, cite it.
