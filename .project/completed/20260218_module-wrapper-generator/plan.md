## 1. Assessment

### What This Component Does

The module wrapper generator (`generation/modules.py`) takes a `CalculationDefinitionData` and a Jinja2 template environment, and renders a TEAx module wrapper Python file via `teax_module.py.jinja2`. The wrapper contains:
- A Pydantic `BaseModel` input class with typed fields
- A `ModuleBase` subclass with `validate_and_fill_default()` and `run()` methods
- An import of the handwritten implementation function from a derived namespace path

The function `generate_teax_module()` handles CalcUsage modules only. FORMULA and aggregation module wrappers are generated by separate functions in `cli/__init__.py` (`_generate_computed_attr_modules()` and `_generate_aggregation_modules()`), both of which also render the same `teax_module.py.jinja2` template with different context dicts. All three paths are part of the REQ-GEN-02 scope but C21 focuses on `generation/modules.py`.

**Issues found during review:**

1. **`generate_teax_module()` uses `calc_def.name + "Module"` for class_name, but `PipelineModule.module_type` uses `derive_module_type()` which includes namespace prefix (e.g., `solarbatterylibrary.EnergyProductionCalcModule`).**
   The class name in the generated file is the short form (`EnergyProductionCalcModule`) — correct because the file is already in the namespace directory. The `module_type` in the registry/YAML is the full namespaced form for disambiguation. For cross-referencing in tests, compare generated class name against `module_type.split(".")[-1]`.
   **Resolution**: Not an inconsistency — different contexts require different forms. Test should use `module_type.split(".")[-1]` for comparison.

2. **`_map_input_type()` in `modules.py` is one of 4 copies with subtle differences (REQ-GEN-06 documented violation).**
   The `modules.py` copy maps `Real` -> `"float"`, `Integer` -> `"int"`, `Boolean` -> `"bool"`, `String` -> `"str"`, with pass-through for unknown types. This may produce different results than the graph builder's type mapping for PipelineModule.inputs.python_type. The test should verify consistency between `_map_input_type()` output and PipelineModule input types for real data.
   **Resolution**: Document any divergence. Not a blocker for C21 conformance — the test verifies current behavior. Phase 7 should consolidate.

3. **`teax_module_stub.py.jinja2` template is dead code.**
   The stub template exists at `src/sysml_codegen/templates/teax_module_stub.py.jinja2` but is never referenced in any source file. It uses a completely different context variable schema (`module_name` vs `class_name`, dict-based `run()` vs keyword-based `run()`). This is a dead template that can be removed in Phase 7.
   **Resolution**: Note in learnings. Not a test blocker.

4. **FORMULA and aggregation generation lives in `cli/__init__.py`, not `generation/modules.py`.**
   C21 scope is `generation/modules.py` which only generates CalcUsage wrappers. The "one wrapper per PipelineModule" AC, applied literally, would require testing all three generation paths. However, per the checklist entry's "Current location: `generation/modules.py`", C21 focuses on the CalcUsage path. FORMULA/aggregation generation conformance could be a separate step or subsumed into Phase 7 consolidation.
   **Resolution**: C21 tests the CalcUsage generation path. Include a structural test counting how many PipelineModule types exist and which are covered by `generate_teax_module()` vs other generators.

5. **CalcUsage-to-PipelineModule mapping requires `build_full_graph_from_snapshot()` for cross-referencing.**
   To verify "input/output types match module definition," we need both the calc_defs (for wrapper generation) AND the ComputationGraph (for expected PipelineModule shapes). The `build_full_graph_from_snapshot()` helper from C17 provides both — it returns `(graph, inputs_dict)` where `inputs_dict["snap"]["calc_defs"]` contains the calc_defs used to build the graph.
   **Resolution**: Reuse the C17/C20 helper. Session-scoped fixtures for efficiency.

### Risks & Unknowns

- **Low risk**: Type mapping divergence between `_map_input_type()` and graph builder may surface mismatches. These would be findings to document, not test failures (the test verifies current wrapper generation behavior against its own type mapping, plus cross-references with the graph).
- **Low risk**: Multi-output modules in solar_battery (PVModuleCostCalc, BatteryPackCostCalc — 5 outputs each) exercise the `is_multioutput` code path naturally.
- **No risk**: No production code changes expected. Phase 6 is conformance-only.

### Implementation Notes

1. **CalcUsage-to-PipelineModule mapping**: The `build_full_graph_from_snapshot()` helper returns `(graph, inputs_dict)`. The `inputs_dict["snap"]["calc_usages"]` contains all CalcUsageData with `calc_def_name` fields. The `inputs_dict["snap"]["calc_defs"]` has the CalculationDefinitionData objects. Build a `calc_def_map = {cd.name: cd for cd in snap["calc_defs"]}` and find CalcUsage PipelineModules by filtering `graph.modules` for `not m.is_computed_attribute and not m.is_aggregation`.

2. **Matching PipelineModule to calc_def**: Each CalcUsage PipelineModule's `module_type` ends with `CalcModule` or similar. The calc_def_name can be derived from the module's `module_type` by taking `module_type.split(".")[-1].replace("Module", "")` (this may not be exact due to sanitization). A more reliable approach: the backtracking result's `required_usages` map usage names to `calc_def_name`, and the module `name` matches `get_module_name(usage.qualified_name)`. Use `inputs_dict["result"].required_usages` to build a `module_name -> calc_def_name` mapping.

3. **Parsing generated code**: Use `ast.parse()` to parse generated Python code. Walk the AST for `ast.ClassDef` nodes to find the input model class and module class. Extract field names from the input model's class body.

4. **Template environment**: Same as C20 — `jinja2.Environment(loader=jinja2.FileSystemLoader(TEMPLATE_DIR), trim_blocks=True, lstrip_blocks=True)`.

5. **Multi-output natural coverage**: solar_battery has PVModuleCostCalc (5 outputs) and BatteryPackCostCalc (5 outputs). These exercise `is_multioutput() == True` naturally. catf_mfe should be checked but likely has multi-output modules too.

6. **Cross-referencing type mappings**: For each CalcUsage PipelineModule input, find the corresponding calc_def input attribute and verify `_map_input_type(attr)` == `module_input.python_type`. Mismatches indicate the REQ-GEN-06 consistency violation. Document but don't fail — the test should report mismatches as findings.

3. **catf_mfe has 42 CalcUsage modules, 0 FORMULA, 0 aggregation**: 100% coverage by `generate_teax_module()`. solar_battery has 8 CalcUsage + 2 FORMULA + 4 aggregation = 14 total, so `generate_teax_module()` covers ~57%.
4. **CalcUsage-to-calc_def mapping via BacktrackingResult.required_usages works reliably**: `usage.qualified_name.lower()` matches `PipelineModule.name` for all CalcUsage modules in both models.
5. **Multi-output modules exercised naturally**: solar_battery PVModuleCostCalc and BatteryPackCostCalc (5 outputs each) test the multi-output code path.
