# 21 -- Pipeline YAML Generation: Channel Formats and Type Rules

## What pipeline.yaml Contains

The pipeline YAML defines execution order, module wiring, entry points, and
exit points. Generated by `generation/pipeline.py:24-63` from `ComputationGraph`
alone -- no raw extraction data needed. This is the "gold standard" generator
(see [doc 08](08-generation.md)).

---

## Design Constraints

Two constraints govern pipeline YAML correctness:

**Entry point channels require a `param_group.` prefix**: Pipeline YAML must
reference entry points as `system_design.SolarBatteryDesign__...wattage`, not
bare `SolarBatteryDesign__...wattage`. TEAx uses the prefix to locate the
correct JSON input file. `pipeline.py:168-171` applies the prefix from
`InputSource.param_group`, which must be non-None for every entry point.
Entry points created during orphan classification (graph_builder.py step 6.8)
or aggregation module building get their `param_group` from the
[parameter group deriver](17-parameter-group-deriver.md).

**All numeric types must be `float`**: TEAx expects all numeric pipeline
values as `float`. This includes multiplicity entry points
(e.g., `module_count`, `inverter_count`) — `graph_builder.py` uses
`python_type="float"` for all numeric inputs, with no exceptions.

---

## Requirements

| ID | Requirement | Traces to | Verified by |
|----|-------------|-----------|-------------|
| REQ-PY-01 | ALL entry point sources in pipeline YAML SHALL include a `param_group.` prefix | TEAx JSON resolution | No YAML entry point line matches `^\s+\w+: \w+ [A-Z]` (unprefixed QN) |
| REQ-PY-02 | `InputSource.param_group` SHALL NOT be None for any entry point in the ComputationGraph | TEAx JSON resolution | `all(ep.param_group is not None for ep in graph.entry_points)` |
| REQ-PY-03 | ALL numeric pipeline input types SHALL be `"float"` (including multiplicity counts) | TEAx type contract | No `int` type in any YAML `inputs:` line |
| REQ-PY-04 | MODULE_OUTPUT sources with `field_name == "root"` SHALL append `.root` to the channel name | Channel format | All single-output references in YAML end with `.root` |
| REQ-PY-05 | `channel_field_map` SHALL contain an entry for every `ModuleOutput` in the graph | Wiring completeness | `len(channel_field_map) == sum(len(m.outputs) for m in graph.modules)` |
| REQ-PY-06 | Exit point type SHALL be `RootModel[T]` when `field_name == "root"`, else `T` | Schema consistency | Exit point types match their upstream module output types |
| REQ-PY-07 | Entry point module inputs SHALL list one JSON file per `ParameterGroup` | JSON resolution | `len(entry_fusion.inputs) == len(graph.entry_point_groups)` |

## Input Source Formatting Rules

Every `ModuleInput` has a `source` ([`InputSource`](09-data-models.md)) that
is either a module output or an entry point. The formatting differs:

### MODULE_OUTPUT Sources (lines 155-164)

```python
channel = inp.source.producer_channel
producer_field = channel_field_map.get(channel, "")
if producer_field == "root":
    source = f"{channel}.root"    # Single-output: extract .root (REQ-PY-04)
else:
    source = channel              # Multi-output: use channel directly
```

**Examples**:
```yaml
# Single-output upstream (RootModel[float]):
p_net_mw: float Design__plant__p_net_kw__p_net_kw.root

# Multi-output upstream (named field):
material_cost: float Design__plant__pv_module__cost_model__material_cost
```

### ENTRY_POINT Sources (lines 166-171)

```python
# REQ-PY-01: param_group prefix is MANDATORY
source = f"{inp.source.param_group}.{inp.source.qualified_name}"
```

**Format**: `{param_group}.{qualified_name}` -- ALWAYS includes param group.
Per REQ-PY-02, `param_group` must never be None. The three param groups are:
- `design_params` -- [DESIGN_ATTRIBUTE](06-entry-point-classifier.md) entry points
- `library_params` -- [LIBRARY_DEFAULT](06-entry-point-classifier.md) entry points
- `system_design` -- orphan/hierarchy entry points (multiplicity, `:>>` overrides)

**Examples**:
```yaml
# Design attribute:
p_net_mw: float design_params.Design__plant__energy_production__p_net_mw

# Library default:
cost_per_watt: float library_params.Design__plant__pv_module__cost_model__cost_per_watt

# System design (hierarchy entry point):
module_count: float system_design.SolarBatteryDesign__solar_battery_plant__module_count
```

## The channel_field_map (REQ-PY-05)

Pre-built lookup from all module outputs. Maps channel name to field name.

```python
channel_field_map = {
    out.channel_name: out.field_name
    for module in graph.modules
    for out in module.outputs
}
```

**Purpose**: Determines whether to append `.root` when consuming an upstream
module's output (REQ-PY-04). If producer's `field_name == "root"`, consumer
must extract `.root` from the `RootModel[float]` wrapper.

---

## Type Mapping Rules (REQ-PY-03)

Input types are set during module construction in [graph_builder.py](07-graph-assembly.md),
not during YAML generation. The YAML passes through `ModuleInput.python_type`.

| Context | Type | Source | REQ-PY-03 |
|---------|------|--------|-----------|
| CalcUsage inputs | `"float"` | graph_builder.py:1521 | Compliant |
| Computed attribute inputs | `"float"` | graph_builder.py:847 | Compliant |
| Aggregation term inputs | `"float"` | graph_builder.py:1145 | Compliant |
| Aggregation multiplicity | `"float"` | graph_builder.py:1169 | Compliant |

Multiplicity counts use `python_type="float"` like all other numeric inputs,
ensuring uniform type handling across the pipeline.

## Output Type Rules (REQ-PY-06)

```python
if out.field_name == "root":
    output_type = f"RootModel[{out.python_type}]"   # Single-output
else:
    output_type = out.python_type                     # Multi-output field
```

**Examples**:
```yaml
# Single-output module:
outputs:
  root: RootModel[float] Design__plant__energy_production__annual_energy_mwh

# Multi-output module:
outputs:
  material_cost: float Design__plant__pv_module__cost_model__material_cost
  fab_cost: float Design__plant__pv_module__cost_model__fab_cost
```

## Entry Point Module (REQ-PY-07)

The first YAML module loads JSON files -- one per [`ParameterGroup`](09-data-models.md):

```yaml
entry_fusion:
    module_type: EntryPoint
    inputs:
      library_params: LibraryParams ../inputs/library_params.json
      design_params: DesignParams ../inputs/design_params.json
      system_design: SystemDesign ../inputs/system_design.json
```

Comment lines above each pipeline module indicate origin type:
- CalcUsage: `# solarbatterylibrary.EnergyProductionCalcModule`
- FORMULA: `# source: computed_attribute ({module_type})`
- Aggregation: `# source: aggregation ({module_type})`
